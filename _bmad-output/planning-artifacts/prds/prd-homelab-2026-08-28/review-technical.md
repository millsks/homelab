# Technical Feasibility Review — Project Asgard

## Verdict

The architecture is sound in its bones — Proxmox + k3s + FreeIPA + Keycloak + NFS is a well-travelled combination and roughly 80% of the FRs will build more or less as written — but the PRD systematically over-promises at the seams where a *capability* has to be honoured *uniformly* by heterogeneous appliances, and three of those over-promises are load-bearing: the "NAS shuts down last" ordering that the whole power design is derived from is not something DSM actually implements (DSM enters *Safe Mode*, which is not a power-off, on an independent timer with no dependable client handshake); the "15 minutes to full revocation everywhere" claim is contradicted by Proxmox's own 2-hour session ticket and by Keycloak's LDAP federation not propagating FreeIPA's `nsAccountLock`, so `ipa user-disable` alone does *not* revoke access and SM-3's "no second list to remember" is false as designed; and FR-62's "backups independent of their source" is unsatisfiable for NFS PV and Home Directory data because the only bulk storage target in the inventory *is* the source. Below that tier sit a cluster of things that work with named caveats — k3s OIDC (fine, but needs `kubelogin` and a break-glass kubeconfig that the shutdown orchestration must also use), FreeIPA replication (fine, but the CA renewal master is a single point of unrecoverable failure unless the replica is explicitly built with `--setup-ca`), and NFS home directories (achievable with `hard` + autofs, but first-login provisioning under an indirect wildcard map does not work, and `soft` is not an acceptable escape). Capacity fits in aggregate with room to spare, but the headroom is fragmented — NFR-6's 20 GB is real cluster-wide and never more than ~11 GB on any single node, which is not the same thing. None of this is fatal; all of it is cheaper to fix in the PRD than in the build.

## Findings

### Identity and SSO

- **[critical]** Disabling a FreeIPA account does not revoke SSO access, and the 15-minute bound is not met (FR-22, FR-35, UJ-5, SM-3) — Keycloak's LDAP user federation in its default `READ_ONLY` + *Import Users = On* mode copies the account into Keycloak's own store and delegates only *password validation* to LDAP. `ipa user-disable` sets `nsAccountLock`, which makes new LDAP binds fail (so fresh interactive logins break, correctly), but Keycloak has **no built-in mapper for `nsAccountLock`** — it ships `msad-user-account-control-mapper` for Active Directory's `userAccountControl` and nothing equivalent for 389-ds/FreeIPA. This is a confirmed, still-open upstream gap (keycloak/keycloak issue **#21502**, "Map Federated LDAP `nsAccountLock=true` to disable user") whose documented answer is *write a custom LDAP mapper SPI*. The imported Keycloak user stays `enabled=true`. Consequences: (a) the existing Keycloak SSO cookie remains valid until *SSO Session Idle* (default 30 min) or *SSO Session Max* (default 10 h); (b) a `refresh_token` grant is validated against Keycloak's local user record, not against LDAP, so **refresh after disablement succeeds** — directly contradicting FR-35's second testable consequence; (c) periodic LDAP sync does not fix this, because the sync mappers do not carry lock state either; (d) the federation provider's *Cache Policy* (`DEFAULT` by default) independently delays when Keycloak would even observe a change, so `NO_CACHE` or `EVICT_DAILY` is worth setting on principle. So SM-3's "there is no second list to remember" is false: revocation requires `ipa user-disable` **plus** a Keycloak action. *Fix:* Rewrite FR-22/FR-35 to admit a two-step revocation Procedure and make it the automation: `ipa user-disable <u>` → `kcadm.sh update users/<id> -s enabled=false` → `kcadm.sh create users/<id>/logout` (kills SSO sessions and offline tokens). Alternatively write a custom Keycloak LDAP mapper for `nsAccountLock`, or set *Import Users = Off* and accept the per-request LDAP cost — but note neither alone kills a live SSO session, so the explicit logout call is required regardless. Also set realm *SSO Session Idle* ≤ 15 min so the cookie can't outlive the stated window. Add an FR: "revocation is a single Procedure, not a single action."

- **[critical]** Proxmox VE cannot honour a 15-minute token lifetime (FR-35, FR-32) — PVE 7.0+ supports an OpenID Connect realm, and **PVE 8.4 (April 2025)** added `groups-claim` / `groups-autocreate` / `groups-overwrite` so Keycloak group claims can drive PVE group membership (note: claimed group names get a `-<realm>` suffix). But Proxmox uses OIDC *only for the initial login exchange*. It then mints its **own PVE authentication ticket, lifetime ~2 hours, silently auto-renewed by the web GUI while a tab stays open**, and it implements no refresh-token use, no mid-session IdP re-validation, and **no OIDC backchannel logout**. A Proxmox session established before disablement therefore survives the 15-minute window and can be renewed indefinitely by an idle browser tab. FR-35's fourth consequence ("the 15-minute bound is stated in each Relying Party's configuration") cannot be satisfied because Proxmox has no such configuration knob. *Fix:* Restate FR-35 as "≤15 minutes for token-validating Relying Parties (Kubernetes API, oauth2-proxy-fronted services, the operator's own Workloads); ≤2 hours for Proxmox VE; ≤DSM logout-timer for Nidavellir," and add to the revocation Procedure an explicit `pveum user delete <u>@<realm>` or `--enable 0`. Lower confidence flag: the exact 2-hour ticket lifetime is community-sourced rather than from a Proxmox doc page — verify against your installed version before writing it into a runbook.

- **[high]** Synology DSM will not auto-provision accounts from OIDC, so "one Account, never duplicated" breaks at the NAS (FR-32, FR-30, §12 assumption) — DSM 7.2+ does support a *generic* third-party OIDC provider (Control Panel → Domain/LDAP → **SSO Client** → "Enable OpenID Connect SSO service"), so the §12 assumption resolves **positive on support**. But DSM **matches the configured username claim against an account that must already exist in DSM** (local, LDAP, or AD) — it does not create users from claims. It also covers **the DSM web UI only**: SMB, NFS, SSH, and the mobile apps are untouched by SSO. This means FR-30's "Accounts are not created directly in the IdP" is satisfied while the *spirit* of one-account-everywhere is not, unless DSM is also joined to the Directory. *Fix:* Make the DSM **LDAP join to FreeIPA a requirement, not an option** — it is what supplies the account DSM's SSO client then matches, and it is separately load-bearing for FR-15 (see below). Community consensus (multiple independent write-ups, not vendor-documented) is that DSM's simple-bind client must be pointed at FreeIPA's **`cn=compat,dc=asgard,dc=home,dc=arpa`** schema-compatibility tree rather than the native `cn=users,cn=accounts` tree, with a Custom server type and explicit user/group filters. Budget a spike for this; it is the least-standard integration in the design. Also note DSM's SSO client needs the discovery endpoint over HTTPS with a browser-trusted cert — Draupnir's root must be in the *operator's browser*, not just on Asgard hosts (see FR-28 finding).

- **[high]** A single Keycloak on a single PostgreSQL negates the redundancy FR-25 buys (FR-25, FR-30, NFR-16) — FR-25 makes the Directory survive loss of one instance, and the rationale explicitly says "the Directory is a runtime dependency of the IdP and therefore of every Relying Party." But `forseti` is one VM and `fafnir` is one VM. Losing either takes down every Relying Party in §4.7 — which is the exact outage FR-25 was written to prevent — and NFR-16's "identity … tolerates loss of one Node" is false the moment the node hosting Keycloak or its database dies. The redundancy is being bought one layer below where the failure actually lands. *Fix:* Either (a) drop FR-25 to v2 and be honest that identity is single-instance in v1 (cheapest, and consistent with §6's "not a high-availability production system"), or (b) if FR-25 stays, add an FR requiring the IdP to survive loss of one Node too — two Keycloak instances share a database, so the practical minimum is a second Keycloak VM plus a decision about the DB, which is expensive. Recommend (a), with the caveat rewritten to say what is and is not covered.

- **[high]** Keycloak's LDAP failover between FreeIPA replicas is ordered-and-lazy, not clean (FR-25, FR-30) — Keycloak's `connectionUrl` does accept space-separated LDAP URLs and the underlying JNDI provider tries them left-to-right, so basic failover exists. Three problems: failover is **timeout-driven, not liveness-probed** — against a silently-dropping or firewalled replica the full connection timeout is burned per URL before moving on; Keycloak's LDAP connection **pooling** can hand out stale pooled connections that each fail once before being discarded; and with `connectionTimeout` / `readTimeout` (LDAP provider → Advanced Settings) left unset the effective timeout is the OS TCP timeout, potentially minutes, so a wedged-but-listening replica blocks Keycloak request threads rather than failing over. There is also upstream history here worth knowing: multi-URL failover has had regressions (keycloak/keycloak **#19354**, space-delimited URLs broken in 21.0.1) and an open correctness issue (**#42883**) — so verify the behaviour on your Keycloak version rather than assuming it. FR-25's fourth consequence — "a Directory instance can be patched and restarted without interrupting authentication to any Relying Party" — is therefore too strong; you will see a window of failed logins. The same applies to SSSD on the hosts: once SSSD marks a server offline it stays offline for `offline_timeout` (default 60 s, backing off toward 3600 s), so host logins fall back to cache rather than failing over instantly. *Fix:* Set Keycloak's `connectionTimeout=5000` and `readTimeout=10000` explicitly and list both replicas; on the SSSD side use `ipa_server = _srv_` so SRV-based discovery does the failover. Soften FR-25's fourth consequence to "authentication resumes within a bounded, stated interval" and state the interval. If a genuinely seamless answer is wanted, front the two replicas with a keepalived VIP — but that is a new component and probably not worth it here.

- **[medium]** FR-23 (offline credential caching) and FR-22 (disable revokes host access) contradict each other (FR-22, FR-23, FR-20) — FR-23 mandates `cache_credentials = true` so a previously-authenticated Account can log in with the Directory down. FR-22 states unconditionally that "Authentication fails on every host after the Account is disabled." Both cannot hold: a host in SSSD offline mode will happily accept the cached credential of an account disabled five minutes ago, and SSSD's `offline_credentials_expiration` defaults to `0` (never expire). Same conflict applies to FR-20's "a password change takes effect everywhere without per-host action" — the old password keeps working offline. *Fix:* Scope FR-22's consequence to "while the Directory is reachable from the host," and add a consequence to FR-23 setting `offline_credentials_expiration` to a bounded value (7 days is the usual choice) so the cached-credential window is stated rather than infinite. Note in the runbook that revoking an account while a host is offline is a known gap requiring the host to reconnect.

- **[medium]** Grafana's session outlives the IdP token unless explicitly configured (FR-52, FR-35) — Grafana's `generic_oauth` works fine against Keycloak, and group claims map via `role_attribute_path` (a JMESPath over the token) for org roles. Two caveats worth writing down: **Team Sync via `groups_attribute_path` is a Grafana Enterprise/Cloud feature**, so FR-52's "Group membership determines view and edit permissions" is achievable with `role_attribute_path` (Viewer/Editor/Admin) but *not* via Grafana Teams on OSS. And for generic OIDC providers `use_refresh_token` **defaults to false**, which means Grafana will not check access-token expiry and the session runs on Grafana's own clocks: `login_maximum_lifetime_duration` (30 d default) and `login_maximum_inactive_lifetime_duration` (7 d; sources disagree, verify against your `defaults.ini`). The `accessTokenExpirationCheck` feature toggle was removed in **Grafana 10.3.0** and folded into `use_refresh_token`. *Fix:* Set `use_refresh_token = true`, add `offline_access` to `scopes`, and set `login_maximum_inactive_lifetime_duration = 15m` explicitly. Add "Grafana on OSS maps groups to org roles, not Teams" to the FR-52 notes.

- **[medium]** FR-34's "not reachable bypassing the proxy" has no enforcement plane on a flat LAN (FR-34, NFR-14, §6 non-goal) — inside Kubernetes this is achievable: k3s ships a NetworkPolicy controller by default, so a default-deny plus an ingress-only allow works. Outside Kubernetes it does not: a Guest VM fronted by oauth2-proxy sits on the same flat /24 as every household device with no VLAN, no firewall, and an unmanaged switch, so its backend port is reachable directly by anything on the LAN. *Fix:* Add a consequence requiring host-level `nftables` on any Guest fronted by a proxy (deny except from the proxy's address), and restrict LoadBalancer/NodePort exposure in Yggdrasil to the ingress controller only — everything else ClusterIP. This is the one place where "not segmented" costs a real control, and it should be stated rather than assumed away.

### Kubernetes

- **[medium]** k3s API-server OIDC works, but the flag path and the kubectl client both need stating (FR-39) — this one **works as specified**, with mechanics the PRD should not leave to discovery. k3s has no `--oidc-*` flags of its own; you pass the standard kube-apiserver flags through, preferably in `/etc/rancher/k3s/config.yaml` (which survives upgrades) rather than on the CLI:

  ```yaml
  kube-apiserver-arg:
    - "oidc-issuer-url=https://forseti.asgard.home.arpa/realms/asgard"
    - "oidc-client-id=kubernetes"
    - "oidc-username-claim=preferred_username"
    - "oidc-groups-claim=groups"
    - "oidc-ca-file=/etc/rancher/k3s/draupnir-ca.pem"
  ```

  `oidc-ca-file` must point at the Draupnir root **on the server node's filesystem** — k3s runs the apiserver in-process, so a host path is correct. Keycloak needs a *Group Membership* protocol mapper with "Full group path" **off** so the claim is `["platform-admins"]` not `["/platform-admins"]`, emitted into the ID token; group names then bind to `ClusterRoleBinding` subjects of kind `Group`. On the client side, plan on **`kubelogin` (`kubectl oidc-login`)** as an exec credential plugin from day one: kubectl 1.26 removed the cloud-specific in-tree auth providers and Kubernetes documentation now steers all OIDC use toward exec plugins, so the legacy in-tree generic `oidc` provider is frozen/legacy even where it still compiles. Worth naming as a forward path: **structured authentication config** (`--authentication-config`, `AuthenticationConfiguration`) went beta in **k8s 1.30** and GA in **1.34**, supports multiple JWT authenticators and CEL claim mapping, and hot-reloads the file — strictly better than the flags above once the cluster is on a recent enough k3s. *Fix:* Add these as explicit consequences under FR-39 so the architecture workflow does not have to rediscover them, and add an FR-39 consequence that the Draupnir root is a *prerequisite* of the k3s server build — a Norn that cannot validate Keycloak's cert comes up with OIDC silently non-functional.

- **[medium]** What breaks when Keycloak is down, and the break-glass path the shutdown sequence also depends on (FR-39, FR-57, FR-10) — the apiserver validates JWTs offline against a cached JWKS, so **in-flight tokens keep working while Keycloak is down**, but they are 15-minute tokens (FR-35) and cannot be refreshed, so OIDC administration dies within 15 minutes of a Keycloak outage. The static break-glass credential FR-39 requires already exists: `/etc/rancher/k3s/k3s.yaml`, a client cert against k3s's own CA, entirely independent of the IdP. Two things follow that the PRD does not say. First, **the power-loss orchestration in FR-57 phase 1 must use that static kubeconfig, not OIDC** — by the time you are draining workloads, Keycloak or its database may already be stopping, and an orchestration that depends on the IdP to shut the IdP down is circular. Second, `k3s.yaml` is regenerated on cluster rebuild, so FR-39's "stored outside Asgard" needs a stated refresh trigger or the escrowed copy will be stale exactly when it is needed. Reassuring, and verified in the apiserver source: when the OIDC issuer is unreachable at boot the authenticator **initialises asynchronously** — a goroutine polls discovery every 10 s — so the apiserver **starts normally**, surfaces the failure through a health check, and simply 401s OIDC requests until Keycloak returns. A Norn rebooting during a Keycloak outage will therefore come up healthy and administrable by certificate. *Fix:* Add a consequence to FR-57 that the drain step authenticates with the static credential; add a consequence to FR-39 that the escrowed kubeconfig is re-escrowed after any Yggdrasil rebuild.

- **[high]** FR-9 and NFR-23 are unsafe as blanket statements for etcd members and Directory replicas (FR-9, NFR-23, FR-37) — "Snapshot-before-change is available for every Guest, so experimentation is cheap by default" is a footgun for exactly two guest classes. Rolling a single Norn back to an older snapshot reintroduces a stale etcd member with a rewound revision into a live raft cluster; the documented recovery is to remove and re-add the member, not to roll back. Rolling a FreeIPA replica back desynchronises 389-ds multi-supplier replication (RUV/CSN divergence), and FreeIPA explicitly warns against VM-snapshot restore of IPA servers. Both are the kind of thing UJ-6 ("break something on purpose") will find the hard way. *Fix:* Add an exclusion clause to FR-9/NFR-23: snapshot-and-rollback is a supported Procedure for stateless and single-instance Guests; for etcd members and Directory replicas the supported Procedure is *destroy and rejoin*, not rollback. Write the rejoin Procedure — it is also what UJ-1 needs.

- **[high]** Node rebuild does not "resume hosting Guests"; it recreates them, and the k3s member must be evicted first (FR-7, UJ-1, D11) — FR-7's third consequence says the rebuilt Node "resumes hosting Guests without manual reconfiguration of storage or network." With Guest disks on the destroyed node's local NVMe, those disks are gone; the honest sequence is *recreate from OpenTofu declaration + restore from backup*. Additionally: Proxmox requires care rejoining a node with the same name/IP after `pvecm delnode` (stale `/etc/pve/nodes/<name>` must be purged), and **k3s embedded etcd does not auto-evict a dead member** — a rebuilt Norn rejoining under the same name needs the stale etcd member removed first or the cluster will refuse it. Since D11 is a named final gate, this ordering *is* the deliverable. *Fix:* Reword FR-7's third consequence to "the rebuilt Node is repopulated with its declared Guests, whose data is restored from backup" and add explicit consequences for the Proxmox delnode/rejoin purge and the etcd member eviction. These two steps are precisely the "undocumented steps" SM-1 is measuring.

### Storage

- **[high]** FR-15's first-login home provisioning does not work under an autofs indirect wildcard map (FR-15, FR-16) — the design is right (autofs on-demand `/home` rather than a static hard mount, per addendum §5) but the two requirements collide. An indirect wildcard map (`/home  /etc/auto.home` with `*  -fstype=nfs4  nidavellir:/volume1/homes/&`) can only mount a directory that **already exists on the NAS**. `pam_mkhomedir`/SSSD's `mkhomedir` runs on the client and would have to `mkdir` inside the automount path, which triggers a mount of a nonexistent export and fails. Separately — and this is the harder blocker, confirmed in Red Hat KB 1411233 and the SSSD/FreeIPA lists — NFS **`root_squash` remaps the client's root to `nobody`**, so client-side `pam_mkhomedir` cannot create or `chown` the directory even on a working static mount. So FR-15's third consequence — "First login provisions a Home Directory without manual intervention" — does not hold as designed. *Fix:* Provision homes **server-side**, not client-side. Cleanest: join DSM to FreeIPA over LDAP (already required by the FR-32 finding) and enable DSM's **User Home** service, which creates `/homes/<user>` for directory users automatically. Failing that, since FR-26 already puts Accounts in the Repository and there is exactly one operator, have the account-creation Automation create the directory and set ownership as part of the same play. Do **not** solve it with `no_root_squash` on the home export.

- **[high]** "Does not hang / no uninterruptible sleep" cannot be bought with `soft`, and `hard` does not fully deliver it either (FR-16) — the trade is real and the PRD should record where it lands. `soft` mounts return `EIO` on timeout; a partially-applied write followed by `EIO` is a documented silent-data-loss path, and the standard guidance is that `soft` is for read-only data only. For Home Directories holding source and dotfiles that is not acceptable, and it would violate NFR-17 ("availability may be sacrificed; integrity may not"). With `hard`, the situation is better than the PRD's phrasing implies: since kernel 2.6.25 NFS RPC waits are `TASK_KILLABLE`, so **`kill -9` does clear stuck processes** (the `intr` option has been a no-op for years and is gone). What still hangs is `df`, `ls /home`, any shell whose CWD is under the mount, and plain `umount` (needs `umount -l`/`-f`). *Fix:* Restate FR-16's first consequence as "processes blocked on the Share are terminable with SIGKILL; no reboot is required to recover" — which is true and testable — rather than "no uninterruptible sleep," which is not achievable. Record the mount options as a consequence: NFSv4.2, `hard`, `_netdev`, `timeo=600`, `retrans=2`, `noatime`, `nconnect=4`; autofs with `--timeout=60` so idle nodes hold no mount at all. Note `softreval` as a targeted mitigation — it lets the client keep serving cached attributes/paths after revalidation times out against a dead server, which is specifically what makes a hung tree unmountable, and it composes with `hard`. Use **autofs**, not `x-systemd.automount`: the latter is a static one-entry-per-mount fstab model and does not do indirect wildcard per-user maps. Add a consequence that PAM/sshd for the Break-glass Account must not stat `/home` (which FR-24's out-of-NFS-path requirement already sets up correctly — that clause is one of the better-specified things in the document).

- **[medium]** NFSv4 identity mapping and DSM export options need to be requirements, not discoveries (FR-15, FR-17) — FreeIPA assigns UIDs from a random high base (typically 9-digit). With `sec=sys` the numbers travel as integers, so this works *provided* the DSM export is set to **"No mapping"** rather than the default "Map all users to admin" or "Map root to admin", and provided the shared folder's POSIX permissions actually permit those UIDs (DSM applies its own ACL layer on shared folders, which will otherwise deny unknown UIDs). Also set DSM's NFSv4 domain to match the clients' `idmapd.conf` domain, enable "Allow users to access mounted subfolders," and allow non-privileged ports if any client needs it. *Fix:* Add these as testable consequences of FR-15 — they are the difference between "the mount succeeds" and "the mount succeeds and you can write to it."

- **[medium]** FR-17 needs two CSI drivers, not one, and the iSCSI path has a k3s-specific version trap (FR-17, FR-18) — FR-17's third consequence ("Volumes can be attached by more than one Workload where declared") requires RWX, which means NFS; FR-18 requires block for PostgreSQL, which means iSCSI. `synology-csi` (SynologyOpenSource, actively maintained — v1.3.1 as of Aug 2026, DSM 7.0+) covers **both** — iSCSI LUNs, NVMe/TCP, SMB, and NFS shared folders — so one driver can serve both classes, which is the tidier answer than pairing it with `nfs-subdir-external-provisioner`. Two requirements follow: every Valkyrie needs **`open-iscsi` installed with `iscsid` running on the host**, and there is a documented k3s issue (k3s-io#11708) where **iSCSI mounts fail with `open-iscsi` 2.1.10 but work on 2.1.9**, leaving pods stuck in `ContainerCreating`. *Fix:* Add a consequence to FR-17 naming the CSI driver as a Repository-declared component with the `open-iscsi` host prerequisite, and pin/verify the `open-iscsi` version in the Valkyrie image build. Note the DS925+'s **M.2 NVMe slots still require Synology-branded drives** even after the DSM 7.3 policy reversal, so "put the Postgres LUN on an NVMe pool" is not free.

- **[medium]** DS925+ third-party drive compatibility — resolved, but verify the DSM version (§12, inventory) — Synology's 2025 Plus-series originally blocked storage-pool creation on non-Synology-branded drives, which would have made the four WD Red Pro 14 TB drives unusable. **Synology reversed this in DSM 7.3**: third-party 3.5" SATA HDDs now create pools with an informational "not on the compatibility list" note rather than a hard block. The inventory is therefore viable. *Fix:* Add "DS925+ ships or is immediately updated to DSM 7.3+" as an explicit precondition in the Repository's bill of materials, alongside the existing UPS compatibility gate (Open Question 5). Confidence: medium-high — corroborated across several independent outlets and Synology's compatibility-policy KB, but I did not retrieve Synology's verbatim current policy text. Check the drives create a pool before committing to the RAID-level decision in Open Question 3.

- **[high]** FR-62 is unsatisfiable for PV and Home Directory data with the listed hardware (FR-62, FR-61, FR-64, §10 risk table) — FR-62 requires backups "stored on a system independent of their source." Home Directories and all NFS PVs live on Nidavellir. The only bulk storage in the inventory is Nidavellir. Backing the NAS up to itself satisfies nothing, and the 1 TB SanDisk SSD is explicitly reserved as offline break-glass escrow (addendum §1) and is anyway a third of the data footprint. FR-64 ("rebuild Asgard from Repository plus backups") inherits the same hole: lose the NAS and you have lost both the data and its backups. This is a bigger gap than the §10 risk row admits — that row says FR-62 "keeps backups independent," which is exactly what it cannot do. *Fix:* Pick one and write it in: (a) a USB drive on the NAS as a Hyper Backup target — weak independence but cheap and better than nothing; (b) an outbound-only cloud target (Backblaze B2 / Synology C2) via Hyper Backup, which does **not** violate NFR-14 since it creates no inbound path — worth stating explicitly because "no internet exposure" reads like it forbids this and it does not; or (c) amend FR-62 to scope it to Node-sourced backups only and move NAS-sourced data to an accepted risk with the §10 row corrected. Option (b) is the only one that actually satisfies the requirement as written.

- **[medium]** Loki's own persistence undercuts FR-50's survival guarantee (FR-50, FR-62) — "Logs survive the destruction of the system that produced them" is satisfied for the *source* hosts but not for `muninn` itself. Loki's boltdb-shipper/TSDB index is known-problematic on NFS, and MinIO explicitly does not support network-filesystem backends, so the obvious "put Loki's object store on the NAS" answers are both bad. *Fix:* Run Loki with filesystem storage on `muninn`'s own VM disk and cover it with `vzdump` to the NAS; then say so in FR-50's consequence, scoping the guarantee to "logs survive destruction of the host that produced them" and accepting an RPO equal to the backup interval for `muninn` itself.

### Certificates

- **[high]** FreeIPA's CA renewal master is a single point of unrecoverable failure, and the replica must be built to take it over (FR-25, FR-27, FR-29) — this is the classic FreeIPA footgun and it lands squarely on three FRs at once. A FreeIPA replica installed without `--setup-ca` cannot issue certificates at all, and without `--setup-dns` cannot answer for the zone — so FR-13 ("more than one resolver"), FR-25 ("more than one Directory instance"), and FR-27 ("one authority issues all internal certificates") all quietly depend on how the *replica* is installed, which the PRD never says. Worse: even with two CA-bearing replicas, the **CA renewal master is a single designated role** — a CA-ful FreeIPA deployment must have exactly one at all times. The dangerous case is specific: removing a server properly (`ipa server-del`) auto-elects a new renewal master among the surviving CA replicas, but a renewal master that is merely **offline or destroyed without being removed from the topology is not auto-replaced**. FreeIPA's own subsystem certificates then silently fail to renew and eventually expire, at which point the deployment is effectively unrecoverable. Note that this is exactly the UJ-1 scenario — destroying `odin` on a Saturday — so the drill will find it. *Fix:* Add consequences to FR-25 requiring the replica be installed with `--setup-ca --setup-dns`; add a consequence to FR-29 requiring `ipa-csreplica-manage set-renewal-master` to be a documented Procedure and that the renewal master's `getcert list` output is monitored with an alert well ahead of expiry (this is a distinct alert from FR-51's generic "certificate expiry approach" — the IPA subsystem certs are the ones that kill you).

- **[medium]** Automatic renewal breaks at the Synology, and probably at the Proxmox hosts too (FR-29, FR-27) — FreeIPA 4.9+ does ship an ACME service (`ipa-acme-manage enable`, directory at `https://<ipa>/acme/directory`), which is the clean answer for cert-manager inside Yggdrasil and turns FR-29 from "hard" to "routine" for Workloads — worth naming in the architecture. It does not help the two appliances. **Synology DSM has no automated import path for an internal CA's certificates**: DSM's ACME support targets Let's Encrypt over public DNS, and internal certs are imported by hand through the UI or via the unofficial `SYNO.Core.Certificate` web API, which breaks across DSM updates. **Proxmox** hosts can be handled with `certmonger` writing `/etc/pve/local/pveproxy-ssl.pem` plus a `systemctl reload pveproxy` post-hook, but that requires enrolling a Debian PVE host into FreeIPA. `freeipa-client` **is** an official Debian package (4.9.11-1 in bookworm, so `ipa-client-install` is available on a PVE 8 host), but it is the least-travelled client platform, it rewrites `nsswitch.conf` and the PAM stack on a hypervisor, and the two recurring Debian/Ubuntu caveats are worth pre-empting: SRV autodiscovery can latch onto the wrong directory service (use `--server` with `--fixed-primary`), and a failed `ipa-client-install` can leave a half-configured host with SSSD's config renamed to `.deleted`, requiring manual cleanup. I found **no** Debian-12- or Proxmox-specific bug reports either way — this is genuinely thin ground, so treat it as plausible-but-unverified and spike it before it becomes a Node build dependency. *Fix:* Amend FR-29 to name Nidavellir as a stated exception with a documented manual renewal step and a calendar alert, or accept an unofficial scripted import and record it as a known-fragile Procedure. For Proxmox, decide explicitly in architecture between full IPA enrolment and a simpler Ansible-driven `ipa-getcert`-less flow (issue via the IPA API from a control host, push the cert, reload) — the latter avoids putting an IPA client on the hypervisor.

- **[medium]** FR-28's "no certificate warning anywhere" excludes the machine the operator actually uses (FR-28, SM-8) — FR-28's consequences cover "every Node and Guest." The operator drives all of this from a workstation that is neither, sitting on the household LAN. SM-8 ("no certificate warning appears anywhere in normal use") is therefore measured somewhere FR-28 does not reach. Compounding it: Firefox uses its own NSS trust store (`security.enterprise_roots` only helps on Windows/macOS), Java has its own `cacerts`, and Python/Node bundle their own CA sets — so "Command-line tools and Workloads validate internal certificates without per-host manual steps" is a strong claim that needs a per-runtime plan. *Fix:* Add a consequence to FR-28 covering the operator's workstation as an explicitly documented (if manual) trust-installation Procedure, and add one requiring a stated mechanism for injecting the Draupnir bundle into Workloads — cert-manager's `trust-manager` distributing a CA ConfigMap is the standard answer and should be named. Also relevant: DSM's OIDC SSO client requires the *browser* to trust Keycloak's cert, so the workstation trust step gates FR-32 as well.

- **[high]** NFR-11 as written is not achievable and should be scoped (NFR-11) — "All service-to-service and operator-to-service traffic within Asgard is encrypted with certificates chaining to Draupnir" is false for a long list of things this design requires: NFS with `sec=sys` is cleartext; iSCSI has no encryption (CHAP is authentication only); k3s's internal control-plane and etcd peer traffic uses **k3s's own generated CA**, not Draupnir, and cannot readily be made to chain to it; PostgreSQL and Redis wire protocols need separate TLS configuration. DSM *does* support Kerberized NFS (`krb5`/`krb5i`/`krb5p`) via keytab import, and FreeIPA can issue that keytab, so `krb5p` is a theoretically available path to encrypted NFS — but the corroboration for the DSM-plus-FreeIPA combination is old (DSM 6.1-era write-ups) and NFSv4 idmapping under Kerberos adds real complexity, so treat it as a stretch exercise rather than a v1 requirement. *Fix:* Rewrite NFR-11 as "all operator-to-service and HTTP service-to-service traffic is encrypted with certificates chaining to Draupnir; storage-plane traffic (NFS, iSCSI) is unencrypted on the trusted LAN, and Yggdrasil's internal control-plane traffic uses k3s's own CA" — and if Kerberized NFS is wanted, make it its own optional FR rather than an implied consequence of NFR-11.

### Power

- **[critical]** DSM's "Safe Mode" is not a power-off, and there is no dependency-ordered handshake — the controlling constraint does not hold (FR-56, FR-57, FR-58, addendum §9) — the design derives everything from "the NAS must power down last but is also the NUT server." DSM's actual behaviour: on the configured trigger it enters **Safe Mode**, which stops services and unmounts volumes but **leaves the unit running**, waiting for power to return. It only truly powers off if you additionally tick **"Shut down UPS when the system enters Safe Mode"** — which tells the *UPS to cut its own output*, killing every outlet at once, including the switch and any node still shutting down. So FR-57's "Nidavellir is the last device to power off" is either not achieved (Safe Mode, still powered) or achieved by an action that violates FR-58 ("all shutdown participants remain powered until they act"). Second: the ordering itself is a **timer race, not a handshake**. DSM's "Time before Synology NAS enters Safe Mode" is a free numeric value with a Second/Minute/Hour unit, and DSM's customised NUT build is reported to proceed into Safe Mode without dependably waiting for clients — `HOSTSYNC` edits are also reported to be silently overwritten when the UPS network service is toggled in the GUI. Third, a concrete detail the runbook will need: DSM's `upsd` ships **hardcoded credentials `monuser` / `secret`** with UPS name `ups` (`MONITOR ups@<nas> 1 monuser secret slave`), not changeable from the GUI. *Fix:* Rewrite FR-57's second consequence from "Nidavellir is the last device to power off" to "**Nidavellir stops serving storage last**, after every Node has completed shutdown" — that is the property the design actually needs and it is achievable. Make the ordering explicitly time-based and add a consequence stating the margin: Nodes trigger on `ONBATT` after a short delay; DSM's Safe Mode timer is set to at least *2×* the measured worst-case Node shutdown time. Add the FR-60 Drill as the only acceptable evidence (already there — good) and have it measure the *actual* gap, not just that the sequence completed. Decide and record whether the NAS ever powers off at all or simply sits in Safe Mode until mains returns; the latter is probably fine and simpler, but it must be a decision, not a surprise. Confidence: high on Safe-Mode semantics and the hardcoded credentials; **medium** on the HOSTSYNC unreliability — that rests on convergent community reports rather than a first-party statement, so treat it as "do not depend on it" rather than "proven absent."

- **[high]** The ~60-second-per-phase budget is not credible against Proxmox's default guest shutdown timeouts (FR-56, addendum §9 table) — `qm shutdown` waits up to **180 seconds** per guest by default, and `pve-guests.service` shuts guests down serially per node according to their `startup`/`shutdown` order with `up`/`down` delays. A node hosting a Valkyrie, a Norn, and a service VM can therefore consume 9 minutes on its own if any guest is slow to stop — against an 8–12 minute total battery budget. Additionally, OpenTofu-provisioned VMs do **not** get `onboot=1` or a `startup=order=N,up=X,down=Y` setting unless it is declared, so the "dependency order" FR-57 requires does not exist by default. *Fix:* Add consequences to FR-57 requiring (a) every Guest declaration in the Repository to carry an explicit `onboot` and `startup` order/up/down, and (b) a reduced per-guest shutdown timeout with a stated forced-stop fallback. Note that Proxmox has **no cross-node shutdown ordering** — ordering is per-node only — so the cross-node sequencing in phases 1–3 has to be orchestrated by the drain script, not by Proxmox. Then have FR-60's Drill measure per-phase durations, not just the total.

- **[high]** Proxmox HA's default shutdown policy will fight the shutdown sequence (FR-57, FR-37, FR-38) — if Proxmox HA is enabled at all (and FR-38's "no two Control Plane Guests share a Node" invites HA groups as the enforcement mechanism), the cluster's default `shutdown_policy` is `conditional`, under which a node *poweroff* causes its HA-managed guests to be relocated to surviving nodes. During a cluster-wide power event that is precisely wrong: nodes 1–3 shutting down will try to migrate their guests onto node 4, which is itself about to shut down, over a network whose switch is on a finite battery. *Fix:* Either avoid Proxmox HA entirely — k3s already provides Workload-level HA and FR-38 can be enforced by declared placement in OpenTofu rather than by HA groups — or set `ha: shutdown_policy=freeze` cluster-wide and make it a Repository-managed setting with a consequence under FR-57. Flagging moderate uncertainty on the exact semantics of `conditional` in your PVE version; verify before writing the runbook, but do not leave it at the default.

- **[medium]** The power-loss alert cannot leave the LAN, because the router is not on the UPS (FR-51, FR-59, Open Question 6) — the outlet budget (addendum §9) puts the four Nodes, the NAS, the switch, and the AP on battery, with two spares. The **ISP router is not on the list**. FR-59 requires that "transfer to battery raises an alert" and FR-51 requires notification "outside the platform's own interfaces" — but with the router unpowered there is no path off the LAN, so the single most important alert in the system is the one that cannot be delivered. Note this also resolves Open Question 6 in a useful direction: outbound-only notification (email/SMTP, ntfy, a webhook) does **not** violate NFR-14, which forbids *inbound* paths — so the channel question is easy once the router has power. *Fix:* Put the ISP router (and, if it is separate, the ONT/modem) on outlet 8. That is what the spare outlets are for, and it converts FR-59 from aspirational to real. Add a consequence to FR-58 naming the router as a required battery-backed device.

### Capacity

- **[medium]** NFR-6's 20 GB is real cluster-wide but never available as a single allocation (NFR-6, NFR-9, §7.1) — the addendum's 100 GB / 28 GB split is arithmetically correct against 128 GB. But once FR-38 pins the three Norns to three different Nodes and the fixed Guests are placed, the best achievable distribution looks roughly like: `odin` 11.5 GB free, `thor` 10.5, `heimdall` 2.5, `tyr` 3.5 — 28 GB total, **maximum ~11.5 GB contiguous**. RAM is not oversubscribed by design (correctly), so an experiment needing 16 GB has nowhere to go despite 28 GB being "free." *Fix:* Restate NFR-6 as a per-Node floor as well as a cluster total — e.g. "≥20 GB unallocated cluster-wide **and ≥8 GB unallocated on at least two Nodes**" — which is what actually makes the headroom usable, and is the number the placement plan should be checked against.

- **[medium]** NFR-6 and NFR-7 cannot both hold after a Node loss (NFR-6, NFR-7, NFR-16) — losing a Node hosting a Valkyrie (16 GB) plus a Norn (4 GB) leaves ~25.5 GB free across the survivors, of which the largest contiguous block is ~11.5 GB. The Norn can restart; the Valkyrie cannot be placed anywhere. NFR-7 anticipates this ("though not necessarily all Workloads") and is satisfied, but the experimentation headroom NFR-6 protects is consumed in the process. *Fix:* Add a sentence to NFR-6 scoping it to the four-Node steady state, so the degraded-mode expectation is stated rather than discovered during a Drill.

- **[medium]** FreeIPA at 3 GB is under-specified, and the PVE overhead figure assumes LVM-thin (§2 capacity model, NFR-9) — a FreeIPA server running 389-ds, the KDC, `named`, **and** the Dogtag CA (a Tomcat JVM) wants 4 GB; 3 GB is below the practical floor and `ipa-replica-install --setup-ca` in particular is where it will bite. Separately, "Proxmox VE overhead 4 × ~1.5 GB" is only true on **LVM-thin**; if local storage is ZFS, the ARC default alone (10% of RAM capped at 16 GB on PVE 8.1+ installers, 50% on older/manual setups) invalidates the model. FR-9's snapshot requirement is satisfied by LVM-thin, so ZFS is not forced. *Fix:* Raise `mimir` and its replica to 4 GB each (headroom 28 → 26 GB, still comfortably over NFR-6); add a consequence to NFR-9 that either local storage is LVM-thin, or `zfs_arc_max` is explicitly capped in the Repository and counted in the capacity model.

- **[low]** The vCPU line is an aggregate that hides a per-Node ceiling (§2 capacity model) — the model shows "Kubernetes workers 16 vCPU," which is 16 across three Valkyries, not per Guest. Worth stating because no single Guest can exceed 8 vCPU on a 4C/8T Node, and a Node carrying a Norn plus a Valkyrie is ~85% committed before any Workload runs. Not a problem — vCPU oversubscription in a lab is fine — but the table reads ambiguously to a downstream workflow. *Fix:* Split the vCPU column into per-instance and total.

- **[low]** Several MVP components are absent from the capacity model (§2 capacity model, §7.1) — `andvari` (Vault), `brokkr` (CI), `sindri` (registry), `ratatoskr` (Redis), `gjallarhorn`, the GitOps controller, `oauth2-proxy`, cert-manager, the CSI drivers, and the reference application are all in §7.1's MVP scope and none appear in the table. If they all run as Workloads inside the 48 GB Valkyrie budget they fit — roughly 12 GB for a realistic set, leaving ~31 GB inside Yggdrasil — but Harbor in particular is ~6 GB with its bundled Postgres and Redis. *Fix:* Add a line to the capacity model for "Workloads within the Valkyrie budget" with an itemised estimate, and consider a lighter registry (Zot, or Gitea's built-in registry — both do OIDC) if Harbor's footprint is unattractive. This is a documentation gap, not a capacity failure.

### Other

- **[high]** PostgreSQL placement: the VM on local NVMe is not just simpler, it is the only option that keeps SSO alive through a NAS outage (FR-18, FR-17, Open Question 2) — both options satisfy FR-18's letter. The differences that matter: (1) **latency** — an iSCSI LUN puts every Postgres `fsync` across 1 GbE to a RAID-5/SHR-1 array of 7200 RPM spinning disks, so commit latency is a network round trip plus a parity write, against a local NVMe write of tens of microseconds; the DS925+'s NVMe slots would fix this but still require Synology-branded drives; (2) **dependency** — Keycloak's database lives here. On iSCSI, a NAS outage takes down Postgres → Keycloak → *every* Relying Party in §4.7, including the DSM web UI you would need to fix the NAS. On local NVMe, `fafnir` and therefore `forseti` ride straight through a NAS outage, which is a materially better failure mode and is what FR-16's "degrades rather than hangs" is trying to achieve at the storage layer; (3) **backup** — a VM is covered by `vzdump` with no new machinery, satisfying FR-47 and FR-61 for free. The iSCSI route's only real advantage is that it is the better learning exercise, which is a stated project purpose and should not be dismissed. *Fix:* Resolve Open Question 2 as **VM on local NVMe for `fafnir`**, and satisfy the learning goal separately by provisioning `synology-csi` with one iSCSI-backed RWO PV for a non-critical Workload. Note the residual: a Postgres VM on local NVMe is pinned to one Node and cannot live-migrate, so losing that Node takes SSO down — which is the same exposure as the single-Keycloak finding above, and should be accepted together with it.

- **[medium]** FR-41's "no manual DNS or certificate step" has a much cheaper answer than the one it implies (FR-41, FR-13) — as written this points at `external-dns` writing into FreeIPA's DNS, which means the **RFC2136 provider with GSS-TSIG** against `bind-dyndb-ldap`. It works, but it is one of the least-travelled paths in external-dns and the Kerberos plumbing is fiddly. *Fix:* Use a wildcard: a single `*.apps.asgard.home.arpa` A record pointing at the ingress VIP, plus one wildcard certificate from Draupnir. Publishing a new Workload then genuinely requires zero DNS and zero certificate action — which is exactly what FR-41 asks for — and removes a whole component. Related: k3s's bundled **ServiceLB (klipper-lb) does not give you a stable VIP** (it binds host ports across nodes), so FR-41's "reachable by hostname without port memorization" wants **MetalLB in L2 mode**, which works fine on a flat LAN. That partly resolves Open Question 4: replace ServiceLB, keep or replace Traefik on its own merits.

- **[medium]** FreeIPA's restore Procedure is topology-wide, not per-instance (FR-63, FR-25) — FR-63 requires an executed, verified restore for "Directory data." Restoring a single FreeIPA replica from an `ipa-backup` while its peer is live produces replication conflicts and RUV divergence; the supported path is to restore one server and then **reinitialise** the others from it (or remove and re-create them). This is the single most likely restore drill to go wrong. *Fix:* Add a consequence to FR-63 that the Directory restore Procedure covers the whole replication topology and states the reinitialisation step, and that the Drill is performed with both replicas present — a restore drill against a single-instance Directory proves nothing about the configuration you will actually be running.

- **[medium]** `home.arpa` and DNSSEC validation (FR-11, FR-13) — `home.arpa` is delegated from `.arpa` without a secure delegation, and DNSSEC-validating resolvers have historically needed explicit handling to avoid treating internal answers as bogus. FreeIPA's `named` runs with DNSSEC validation on by default. *Fix:* Add `validate-except { "home.arpa"; };` (or the equivalent negative trust anchor) to the FreeIPA DNS configuration in the Repository and add a consequence under FR-11 that resolution is verified from a validating resolver, not just from `dig +cd`. **Uncertain:** whether current BIND/FreeIPA versions need this at all — the delegation is *insecure* rather than *broken*, so it may just work. Cheap to test on day one; expensive to debug in month three.

- **[medium]** FR-12 and FR-14 together force static addressing, which the PRD never says (FR-12, FR-14) — FR-12 requires deterministic, pre-known, rebuild-surviving addresses; FR-14 forbids Asgard from taking over DHCP. DHCP reservations would satisfy FR-12 but live on the household router, which is outside the Repository and therefore violates FR-4 ("no configuration required to rebuild any component exists only on a running system"). *Fix:* Add a consequence to FR-12 that Asgard Nodes and Guests use static addressing declared in the Repository, from a range excluded from the router's DHCP pool — and note that the exclusion is the one household-router change the design does require, which is worth surfacing against FR-14's "unchanged."

- **[low]** FR-11's reverse resolution will be incomplete for the shared /24 (FR-11) — FreeIPA will be authoritative for the reverse zone of the LAN subnet, but household devices sharing that subnet will have no PTR records, so reverse lookups for them return NXDOMAIN from Asgard hosts. Harmless, but it will show up as slow or noisy reverse lookups in NFS and SSH logs. *Fix:* Scope FR-11's second consequence to "every Node and Guest" (which it already says) and add a note that non-Asgard addresses in the shared subnet are deliberately absent.

- **[low]** Keycloak event logging is off by default and FR-36 assumes it is on (FR-36, NFR-15) — Keycloak does not record login events unless the realm's *Login events* / *Admin events* toggles are enabled, and by default events go to the database with an expiration rather than to a log stream. *Fix:* Add consequences under FR-36 requiring realm event configuration in the declarative realm definition (keycloak-config-cli or the Keycloak Terraform provider), and a stated shipping path — Keycloak → stdout → Promtail/Alloy → Loki is the simple one.

- **[low]** FR-19's NAS telemetry needs a named mechanism (FR-19) — DSM exposes no Prometheus endpoint. Capacity, utilisation, and SMART data come out via **SNMP v3 with the Synology MIBs** (scraped by `snmp_exporter` or a Synology-specific exporter), which must be enabled in Control Panel. *Fix:* Name SNMP as the mechanism in the architecture and add "SNMP enabled on Nidavellir" as a Repository-managed configuration item. Related: for FR-59's UPS metrics, prefer `nut_exporter` running `upsc` against DSM's `upsd` from a Proxmox NUT client over SNMP — it reads the same data the shutdown logic reads, which makes the metric and the trigger consistent.

- **[low]** NFR-13's per-host unique break-glass credentials scale to ~16 secrets on a USB stick (NFR-13, FR-24, FR-55) — four Nodes plus roughly a dozen Guests, each with a unique local password, escrowed on the SanDisk SSD, plus the k3s static kubeconfig and the Draupnir trust anchor. That is workable but it is a real operational burden and the escrow will drift as Guests are created and destroyed. *Fix:* Add a consequence to FR-55 that the escrow is regenerated by the same Automation that creates Guests, so it cannot drift — otherwise NFR-13 quietly becomes "one shared password" within six months, which is the failure mode it exists to prevent.

- **[low]** Disable UPnP on the household router (NFR-14) — NFR-14 asserts no inbound path exists, but consumer routers commonly ship with UPnP/NAT-PMP enabled, and any Workload using a UPnP client library could open one without anyone deciding to. *Fix:* Add a consequence to NFR-14 that UPnP and NAT-PMP are confirmed disabled on the household router, recorded in the Repository as a verified precondition.

## Items flagged as uncertain

These are the claims above where I am relying on convergent community evidence rather than first-party documentation, and which should be verified before they are written into a Runbook:

1. Proxmox's PVE ticket lifetime (~2 hours) and its lack of OIDC re-validation — consistent across forum/dev-list sources, no single authoritative doc page.
2. DSM's unreliability in honouring NUT `HOSTSYNC` — repeatedly reported, never first-party confirmed. Treat as "do not depend on it."
3. DSM SSO's scope being web-UI-only — inferred from the consistent absence of protocol-level SSO claims rather than an explicit statement.
4. The FreeIPA `cn=compat` requirement for DSM's LDAP client — a well-corroborated community workaround, not a documented vendor requirement.
5. Grafana's `login_maximum_inactive_lifetime_duration` default (7 d vs 30 d) — sources disagree; check your `defaults.ini`.
6. DS925+ / DSM 7.3 third-party drive policy reversal — corroborated by several outlets, but I did not retrieve Synology's verbatim policy text. Verify by creating a pool before committing.
7. Whether `home.arpa` needs an explicit DNSSEC exception under current BIND/FreeIPA versions.
8. Proxmox HA's exact `conditional` shutdown-policy semantics in your PVE version.
9. `freeipa-client` reliability on Debian 12 / Proxmox VE specifically — packaged and plausible, but I found no dedicated reports confirming or denying it. Spike it.
10. Keycloak's exact behaviour on `refresh_token` for an LDAP-disabled user — the *absence* of an `nsAccountLock` mapper is confirmed by an open upstream issue; the precise session/refresh consequence is inferred from Keycloak's federation and cache model and may vary by version. It is cheap to test directly and worth testing, because the whole of UJ-5 rests on it.

Two things I expected to be problems and verified are **not**: a k3s server rebooted while Keycloak is unreachable comes up fine (the apiserver's OIDC authenticator initialises asynchronously with a 10 s retry poll, verified in the apiserver source), and the DS925+ takes the four WD Red Pro drives on DSM 7.3+.
