# Adversarial Review — Project Asgard PRD

## Verdict

This PRD is unusually disciplined in *form* — a fixed glossary, globally-numbered FRs, "Consequences (testable)" on every requirement — and that discipline is what makes it dangerous, because it reads as far more settled than it is. The prose confidence is doing work the engineering has not done. Three structural failures sit underneath it: the capacity model in the addendum is missing roughly a third of the components §7.1 puts in MVP scope, so NFR-6's 20 GB floor is already breached on paper before a single VM boots; the backup story (FR-62, FR-64, and the §10 risk row that leans on them) has no independent destination in the hardware inventory and §7.2 forbids buying one, which means the platform's headline recoverability claim is unsatisfiable as scoped; and the Walking Skeleton's S5 and S7 both require deepen-phase capabilities, which falsifies the §12 assumption the plan is built on. Beyond those, the document has exactly **one** numeric requirement in it (FR-35's fifteen minutes) — every other threshold, interval, retention window, and schedule is "defined" by an unnamed party at an unnamed time, which makes a large fraction of the "Consequences (testable)" bullets untestable in practice. And a whole category of month-three reality — time synchronization, CA rollover, patching, power-on ordering, the operator's own workstation — is absent, not deferred. The requirements that *are* here are mostly good. The problem is what is confidently missing.

## Findings

- **[critical]** Backups have no independent destination that exists (FR-62, FR-64, §10 risk row 1, §7.2 "Additional hardware") — FR-62 requires backups "stored on a system independent of their source," and the §10 risk table cites FR-62 as the mitigation for Nidavellir being a single point of failure. But the only bulk storage in the inventory *is* Nidavellir; the `hel` backup tier in the addendum is a Nidavellir share; Persistent Volumes and Home Directories already live on Nidavellir, so backing them up to Nidavellir satisfies nothing. The 1 TB SanDisk is explicitly "not part of the running system" and cannot hold the set anyway. §7.2 forbids additional hardware. So FR-64's "rebuild Asgard from Repository plus backups" is false the moment Nidavellir is the thing that died — which is the exact scenario the risk row claims to mitigate. The document asserts the opposite of what its own constraints permit. *Fix:* either move a backup target into scope as required hardware (a second NAS, a large USB array on a Node, or a cloud object target reachable outbound — NFR-14 permits outbound), or amend FR-62 and the §10 risk row to state honestly that Nidavellir loss is unrecoverable for PV and Home Directory data, and reduce FR-64 to "rebuild everything except Nidavellir-resident data."

- **[critical]** NFR-6's 20 GB floor is already breached by §7.1's own scope — the addendum's capacity model totals 100 GB allocated / ~28 GB headroom, but it omits at least seven components §7.1 puts in MVP: Redis (`ratatoskr`, FR-48), the container registry (`sindri`, FR-43), CI build runners (`brokkr`, FR-43), the secret store (`andvari`, FR-54), the GitOps controller (FR-42), the forward-auth proxy (FR-34), and alerting (`gjallarhorn`, FR-51). Conservatively that is 12–16 GB. Additionally, the model budgets 6 GB for "LDAP directory + replica," but §11 names FreeIPA as the leading candidate and the addendum itself prices FreeIPA at ~4 GB *each* — another 2 GB. Realistic allocation is ~115–120 GB against 128 GB, leaving 8–13 GB. The floor is 20 GB. The scope and the NFR cannot both stand. *Fix:* rebuild the capacity table in the addendum with every §7.1 component enumerated and named, then either cut scope (defer D4's in-cluster build/registry, or the Directory replica) or lower NFR-6 to a number the model actually produces. Do this before architecture, not after.

- **[critical]** NFR-6 measures a quantity that does not correspond to experimentation capacity — even setting the arithmetic aside, "unallocated RAM across the Cluster" is satisfiable while zero useful headroom exists, and violable by a change that costs nothing. Move the registry from a standalone Guest into a Workload on the 48 GB worker pool and NFR-6 improves by 4 GB while actual schedulable capacity is unchanged. Conversely, the 48 GB of worker Guests is counted as *allocated*, so the space where experiments actually run is invisible to the metric. The one NFR guarding the platform's stated purpose ("fearlessness is the actual deliverable") does not measure the thing. *Fix:* restate NFR-6 as two requirements — hypervisor-level unallocated RAM (a smaller floor, for standing up a new Guest), and schedulable-but-unrequested RAM inside Yggdrasil after platform Workloads are accounted (the actual experimentation budget). Give both numbers.

- **[critical]** FR-23 makes FR-22, UJ-5, and SM-3 false — FR-22's consequence is "Authentication fails on every host after the Account is disabled." FR-23's consequence is "Credential caching permits login for a previously-authenticated Account with the Directory offline." SSSD's offline cache has no knowledge that an account was disabled upstream; a disabled operator account logs into every host it has previously touched for as long as the cache is valid, and if the Directory is down there is no upper bound at all. Even online, `entry_cache_timeout` delays propagation. UJ-5's climax — "SSH access to every node stops" — is not what happens, and SM-3 claims to *validate* both FR-22 and FR-35 with a 15-minute bound that applies only to Tokens and was never extended to host login. This is the surviving member of the FR-16/FR-24 class of contradiction: the earlier fix addressed storage, not revocation. *Fix:* add a consequence to FR-23 bounding the offline credential cache lifetime with an explicit number, add a matching bound to FR-22 for host access (it will not be 15 minutes and should not pretend to be), and correct UJ-5 and SM-3 to state the two different windows rather than one.

- **[critical]** The Walking Skeleton cannot be built in the stated order — §12 flags this as an assumption; it is already false in three places. (a) **S5 delivers Forseti, but Keycloak requires a database**, and PostgreSQL (`fafnir`) is D5. The only alternative is Keycloak's embedded dev-mode store, which is not rebuildable, not backed up, and violates FR-4 and FR-40 the moment it is used. (b) **S7 requires a container image built from committed source** — FR-43's consequence is explicit that images are "built from committed source, not a workstation" — but image build and the internal registry are D4. (c) **S7 requires the application to be reached over TLS via an OIDC redirect**, which needs ingress with a Draupnir certificate; that is D3. Keycloak will refuse non-localhost clients over plain HTTP, so this is not a nicety. Three of the seven skeleton epics silently depend on the deepen phase. *Fix:* move a minimal PostgreSQL into S5 (it can be a single Guest on local NVMe, satisfying FR-18 without D5's provisioning Procedure), move minimal ingress-with-TLS into S6, and either move a minimal registry into S6 or amend FR-43 to permit a workstation-built image *for the skeleton only*, with the constraint restored at D4. Then update the §12 assumption to record what was actually required.

- **[critical]** The Walking Skeleton enables network login on all four Nodes before break-glass exists — S4 delivers "`mimir`, single instance; one Account logging into all four Nodes." D2 delivers "credential caching, Break-glass with local homes on every host." §4.5's own description calls the escape hatches "requirements, not caveats," and then sequences them *after* the thing they protect against, on a single-instance Directory, across all four Nodes simultaneously. A botched SSSD or PAM configuration at S4 — the single most common failure in this entire build — locks the operator out of every Node at once with no cached credentials and no local account, on hardware with no IPMI. Recovery is a keyboard, a monitor, and single-user mode on four machines. *Fix:* move FR-24 (break-glass with local homes, per NFR-13 unique per host) and FR-23 (credential caching) into S1/S2 as a hard prerequisite gate for S4. Break-glass costs nothing and must exist before the first PAM change, not after. Additionally, require S4 to be applied to one Node and verified before the remaining three.

- **[critical]** A single 1 GbE NIC per Node carries corosync, NFS, pod, and backup traffic — and FR-65's own rationale condemns it — FR-65 forbids wireless because "cluster membership signalling is latency- and jitter-sensitive" and "ordinary wireless variance is indistinguishable from node loss." That reasoning applies unchanged to a saturated 1 GbE link. Each EliteDesk has one port. A PV restore, a backup window, or a Prometheus remote-write burst will saturate it, corosync tokens will time out, and the Cluster will lose or fence a node — the exact failure FR-65 was written to prevent, arriving from a source the PRD categorizes as merely "slow." §10 files "1 GbE nodes bottleneck all storage traffic" under *performance*; it is an availability defect. No requirement anywhere reserves bandwidth for cluster membership or separates it from storage. *Fix:* reclassify this risk as availability, not throughput. Either bring the USB 3.0 / M.2 2.5 GbE adapters into MVP scope (§7.2 already calls them "cheap" and they are the only remedy available) and require corosync on a separate link, or add an NFR bounding storage and backup traffic rate per Node so corosync's token budget survives — and require the backup window to be scheduled, rate-limited, and drilled under load.

- **[critical]** FR-59's power alert cannot be delivered during a power failure — the addendum's outlet budget (§9) lists four Nodes, Nidavellir, the switch, the AP, and a spare. The ISP router and the ONT/modem are **not** on the UPS. FR-51 requires notifications that "reach the operator outside the platform's own interfaces," and FR-59 requires an alert on transfer to battery. During mains loss the upstream path is dead, so the one alert that exists specifically for the unattended-power-loss scenario (UJ-4: "Kevin learns about it from a notification") cannot leave the building. §11 open question 6 half-notices this and frames it as "the operator is away" — the actual problem is that the transport is unpowered even if he is in the next room. *Fix:* put the router and ONT on the UPS (there are two spare outlets) and re-run the ~315 W load math with them included, or state explicitly that power alerts are best-effort and delivered on mains restoration, and stop claiming UJ-4's notification path works. Resolve open question 6 before D8, not during it.

- **[high]** FR-27 and NFR-11 are unachievable for two MVP components — NFR-11 requires *all* service-to-service traffic encrypted with certificates chaining to Draupnir, and FR-27 states "No service presents a self-signed certificate outside that chain." (a) **NFS from Synology DSM has no TLS.** RPC-with-TLS (RFC 9289) is not available on DSM, and the only encrypted alternative is NFSv4 with krb5p, which requires Kerberos — available only if the Directory question resolves to FreeIPA or Samba, and never mentioned as a requirement. Home Directory and PV traffic will be plaintext. (b) **k3s generates its own internal PKI** — apiserver, kubelet, etcd peer certificates chain to a k3s-generated CA, not Draupnir, unless k3s is bootstrapped with a custom CA at install time (which is possible but is a load-bearing architecture constraint nobody has written down). Also unaddressed: corosync's own keys and NUT's plaintext protocol. As written, two MVP-scope subsystems violate a security NFR on day one. *Fix:* scope NFR-11 to "operator-to-service and north-south service traffic," enumerate the explicit exemptions (NFS, k3s internal PKI, corosync, NUT) as recorded exclusions with reasons, and if Draupnir-rooted k3s PKI is actually wanted, state it as a requirement now because it cannot be retrofitted without rebuilding Yggdrasil.

- **[high]** The operator's workstation does not exist anywhere in this PRD — every user journey happens on it. UJ-2 has Kevin opening a URL in a browser and being redirected to Forseti. UJ-3 has him SSHing in. FR-39 has him running `kubectl`. But FR-28 scopes automatic trust distribution to "every Node and Guest," and the workstation is neither. So the browser in UJ-2 gets a certificate warning, and SM-8 ("no certificate warning appears anywhere in normal use") fails on the primary user surface. Likewise FR-11 promises name resolution "within `asgard.home.arpa`" but the workstation resolves via the household router (FR-14), which knows nothing of the domain. The single most-used machine in the system is unmanaged, absent from the Repository, absent from backup, and absent from the assumptions index. *Fix:* add a first-class definition of **Workstation** to the Glossary and requirements covering (a) Draupnir trust anchor installation on it, (b) `asgard.home.arpa` resolution from it, (c) whether its configuration is in the Repository, and (d) explicitly whether it is in FR-64's rebuild scope. Then re-scope FR-28 and SM-8 accordingly.

- **[high]** The Repository's location is unspecified, and every plausible answer breaks a requirement — FR-4 makes the Repository the sole source of truth; FR-64 requires rebuild from "Repository plus backups plus Break-glass credentials, with no other input"; §4.12 says it "will be pushed to GitHub"; the addendum lists Gitea as a candidate OIDC client. If the Repository is GitHub-only, then GitHub and a working internet connection are "other input" to FR-64, and GitOps (FR-42) has a hard external dependency the PRD never acknowledges. If it is self-hosted in Asgard, rebuilding Asgard requires a Repository hosted inside Asgard — a circular dependency of the exact class §3 warns about. If it is both, there is no requirement stating which is authoritative. *Fix:* state where the Repository lives, add an FR requiring a local clone or mirror sufficient to bootstrap a cold rebuild, and add GitHub availability (or its absence) to the §12 assumptions index.

- **[high]** OpenTofu state is a rebuild dependency and a secret store, and is unaddressed — the brief settles OpenTofu for Proxmox provisioning. FR-8 requires that applying a Guest declaration "converges rather than duplicates," which is a property of *state*, not of the declaration. State files routinely contain credentials, which collides with NFR-10. Nothing in §4.12 or FR-64 mentions state at all. Lose it and FR-8 breaks — a re-apply creates duplicate Guests rather than converging. *Fix:* add a requirement covering state location, encryption, backup, and its place in the FR-64 rebuild order; or require an import Procedure that reconstructs state from a running Cluster, and prove it in a Drill.

- **[high]** FR-55 escrows the Draupnir *trust anchor* rather than the Draupnir *private key* — the trust anchor is the public certificate. It is useful for a client; it is useless for reconstituting the authority. If Draupnir is lost, every certificate under FR-27 must be reissued from a new authority and every trust store under FR-28 redistributed — a platform-wide outage during exactly the recovery FR-64 is supposed to make routine. Related and equally absent: **FR-29 covers leaf renewal only.** Nothing covers the CA certificate's own expiry or rollover, and if the Directory resolves to FreeIPA, its CA subsystem certificates are a well-known scheduled bricking event. *Fix:* change FR-55 to escrow the Draupnir private key and any CA subsystem credentials (with a matching NFR on how that escrow is protected), and add an FR for CA renewal/rollover — including redistributing a new anchor via FR-28's automation before the old one expires, and an alert well ahead of CA expiry, not just leaf expiry.

- **[high]** No time synchronization requirement exists anywhere — Kerberos (the FreeIPA path) fails hard above ~5 minutes of clock skew. TLS validity windows, JWT `iat`/`exp`/`nbf` under FR-31 and FR-35, and log correlation under FR-50 all depend on agreeing clocks. Consumer mini-PCs coming back after a UPS-triggered shutdown and a multi-hour outage will not necessarily come up with correct time, and if the ISP router is the NTP path (it is not on the UPS — see above), they will come up wrong together. The 15-minute token bound in FR-35 is meaningless across hosts that disagree by more. *Fix:* add an FR for authoritative internal time distribution — which hosts serve it, what they source from, what happens when the upstream is unreachable at boot — and add clock skew to the alert set in FR-51.

- **[high]** Nothing covers power-on ordering, yet UJ-4 claims the lab comes back — UJ-4's resolution is "Power returns; the lab comes back," and FR-56/57/58 cover only the *down* path. On restore, Nidavellir's four-drive array needs several minutes to become available. Nodes will boot faster, Proxmox will attempt to start Guests, NFS mounts will fail, and Guests whose storage depends on Nidavellir will start broken or not at all. There is no requirement for staggered autostart, boot-order dependency, or a wait-for-storage gate. *Fix:* add an FR for the **Startup Sequence** as the inverse of the Shutdown Sequence — Nidavellir first, storage-availability gate, then Nodes, then Guests in dependency order — and require it to be proven in the same Drill as FR-60. A drill that only proves the down half proves half a Procedure.

- **[high]** Vault's seal state breaks unattended recovery after every power event — `andvari` (D7, FR-54) is a secret store. Auto-unseal requires an external KMS or a transit secret engine; neither exists on a LAN-only platform with no cloud dependency and no second cluster. So every FR-56 shutdown ends with the secret store sealed, and every restart requires the operator to be physically present with key shares held outside Asgard (FR-55) *before* any Workload that depends on FR-54 can start. That directly contradicts UJ-4's unattended premise and FR-56's "lose mains power unattended and find the platform powered down" leading into a lab that comes back. The PRD does not mention seal state once. *Fix:* either state that manual unseal after a power event is accepted and document it as a step in the Startup Procedure (with an alert when the store is sealed), or scope a viable auto-unseal mechanism and price its dependency. Do not leave this to be discovered at the first outage.

- **[high]** FR-25 requires a Directory replica but never requires the two instances to be on different Nodes — FR-38 pins Control Plane Guests apart ("No two Control Plane Guests share a Node"), and no equivalent exists for the Directory, PostgreSQL, or the DNS resolvers under FR-13. NFR-16 asserts identity tolerates loss of one Node "without operator intervention," which is simply false if both `mimir` instances land on `odin`. FR-13's "more than one resolver" has the same hole. *Fix:* add a general placement/anti-affinity requirement covering every component with a redundancy claim — Directory instances, name resolvers, and Control Plane Guests — and make the placement declarative in the Repository per FR-8 so it survives rebuild.

- **[high]** Guest disks are on local NVMe, so NFR-7, NFR-16, and FR-8 promise a failover that cannot happen — the addendum puts VM disks on node-local NVMe ("~3 TB usable for VM disks"). Proxmox HA requires shared storage. So a dead Node's Guests do not restart elsewhere: they are gone with their disks. NFR-16's "tolerate loss of one Node without operator intervention" is only true for components that are *already* redundant and pre-placed (Directory pair, Norn trio); everything else — Keycloak, PostgreSQL, observability, Redis, registry — is simply down until a manual restore. FR-8's "A destroyed Guest is recreated from its declaration" recreates an empty Guest; the data came from FR-61's backups, on a restore path FR-63 requires but which nothing binds to Node loss. Meanwhile NFR-7's arithmetic is tight: 3 surviving Nodes give 96 GB physical, minus ~4.5 GB Proxmox overhead, against ~94 GB of non-worker-plus-two-workers allocation. It fits only after shedding a worker, which nothing automates. *Fix:* say plainly in §10 that Node loss is a *manual restore* event for non-redundant Guests, restate NFR-16 to name exactly which components are covered, and add a Procedure (with a Drill) for "restore the Guests that were on the Node that died" — which is a different Procedure from FR-7's "rebuild the Node."

- **[high]** FR-11's reverse resolution requirement contradicts FR-14 — Asgard shares one flat subnet with the household (§4.3, §6 "Not segmented"). There is exactly one `in-addr.arpa` zone for that subnet, and the household router owns it. FR-11 requires "Reverse resolution succeeds for every Node and Guest"; FR-14 requires "Non-Asgard devices continue to use the household router unchanged." Satisfying both requires either delegating the reverse zone from the router to Asgard's resolvers (a change to household DNS behavior) or two authoritative answers for the same zone (split-brain). The same tension applies to forward resolution of `asgard.home.arpa` from household devices — including the operator's workstation. *Fix:* decide and state the DNS integration model — most likely a conditional forward for `asgard.home.arpa` and a reverse delegation configured once on the router — and amend FR-14 to say "the household router's configuration changes exactly once, in these two specific ways, and that change is recorded in the Repository."

- **[high]** FR-28's trust distribution does not reach the runtimes that actually validate certificates — the consequence claims "Command-line tools and Workloads validate internal certificates without per-host manual steps." Installing an anchor into the OS trust store does not cover Java (`cacerts`, and Keycloak is Java), Node.js (bundled CA list), Python (`certifi`), or Go binaries built with an embedded pool. UJ-2's climax — Kevin's own application validating tokens from Forseti over Draupnir TLS — lands squarely on this. As written, FR-28 will pass a `curl` test and fail the actual journey. *Fix:* extend FR-28's consequences to name runtime trust stores explicitly (Java, Node, Python at minimum) and require the container base image used by FR-43 to carry the Draupnir anchor, so Workloads inherit it rather than each application solving it.

- **[high]** The PRD contains exactly one number — FR-35's fifteen minutes. Everywhere else a threshold is required, the document says "a defined threshold" (FR-19), "a defined period" (FR-49, FR-50), "a bounded interval" (FR-42), "a defined time on battery" (FR-56), "a defined schedule" (FR-61, FR-47), "bounded so storage growth is predictable" (NFR-8) — and no requirement anywhere says *who* defines them, *when*, or *where the value is recorded*. Every one of those "Consequences (testable)" bullets is untestable until someone supplies a number, and nothing in §9 or §11 assigns that. This is a systemic hole, not a set of local ones. *Fix:* add a requirement that every bounded value is recorded in a single Repository-resident table with a stated value and rationale, make populating that table a deliverable of S1, and add its existence to the definition of done for each affected FR.

- **[high]** FR-34's forward-auth proxy violates FR-35 — FR-35 requires every Relying Party to stop honoring a disabled Account within 15 minutes, and its consequence is that "the 15-minute bound is stated in each Relying Party's configuration." A forward-auth proxy is a Relying Party, but its enforcement mechanism is a session *cookie* whose default lifetime is hours, issued once and never revalidated against the IdP until it expires. FR-34's consequences say nothing about cookie lifetime or revalidation. So the class of service the PRD explicitly designs for — "services with no native OIDC support are fronted rather than exempted" — is the class that breaks the revocation guarantee. *Fix:* add a consequence to FR-34 bounding the proxy's session lifetime and/or requiring token revalidation against the IdP at or below the FR-35 window.

- **[high]** NFR-3's "idempotent without exception" collides with the actual primitives, and FR-2 never defines "no changes" — `pvecm create` / `pvecm add` are one-shot and not naturally idempotent; the k3s install script, FreeIPA's `ipa-server-install`, and initial database bootstrap are the same class. Any Automation covering them needs a detection branch, and Ansible's `command`/`shell` modules report `changed` unconditionally unless a `changed_when` is written for each. FR-2's test is "the Automation reports no changes," but the PRD never says in whose terms — `changed=0` in an Ansible play recap? an empty `tofu plan`? both? — nor whether a task that legitimately cannot report change-state is a defect or an exemption. SM-2 claims to measure this "for every Procedure." *Fix:* define the convergence signal precisely per tool in FR-2 (Ansible recap `changed=0` *and* `failed=0`; `tofu plan` producing no diff), and add an explicit policy for non-idempotent primitives: they must be wrapped in a guard that makes the second run a no-op, and any Automation task without a change-detection predicate is itself a defect.

- **[high]** FR-57's ordering is a timer race with no feedback loop — the addendum names DSM as the NUT server and Nidavellir as the last device to power off, resolved by "a delayed timer." DSM's UPS handling triggers on a static condition (minutes on battery, or low battery) and has no mechanism to wait for confirmation that every `upsmon` client has completed shutdown. FR-57's consequence "No Guest is terminated while its storage is already unavailable" therefore has no enforcement — if one Node hangs during shutdown (a stuck Guest, an fsck, a slow drain), the timer fires and Nidavellir powers off underneath it, which is precisely the corruption NFR-17 forbids. The PRD acknowledges the dependency inversion in §4.13's description and then does not solve it. *Fix:* require a positive confirmation mechanism — Nodes signal completion to Nidavellir (a flag file on a share, or a `upssched` handler) and Nidavellir's shutdown is gated on all-confirmed-or-hard-deadline — and add a consequence to FR-57 for the deadline case: what happens, and that it is logged and alerted. Then drill the hung-node case, not just the happy path.

- **[medium]** FR-24 mandates break-glass on every Guest; FR-55 escrows only Nodes — FR-24: "Every Node and Guest has a Break-glass Account." NFR-13: "unique per host, not shared." With the addendum's registry that is roughly nineteen hosts and therefore nineteen unique credentials. FR-55's consequence enumerates only "Break-glass credentials for every Node, plus the Yggdrasil static administrative credential and the Draupnir trust anchor." Guest credentials are mandated and unescrowed. There is also no rotation requirement anywhere, and the escrow medium (a single portable SSD, per the addendum) is one device with no stated encryption, no second copy, and no stated off-site location — a fire takes the lab and the escrow together. *Fix:* align FR-55's enumeration with FR-24's scope, add a requirement for escrow redundancy and off-site storage of at least one copy, and add an FR or NFR for break-glass credential rotation with a stated interval.

- **[medium]** Open question 2's iSCSI answer breaks FR-9 and NFR-23 for `fafnir` — NFR-23 requires snapshot-before-change "for every Guest," and FR-9 requires snapshot and rollback "including disk contents." A raw LVM-over-iSCSI volume is not snapshottable by Proxmox's qemu snapshot mechanism. The addendum prefers the iSCSI route ("the better learning exercise") without noticing it removes the safety mechanism from the one Guest holding the most irreplaceable state. *Fix:* record this trade in §11 open question 2 explicitly, and if iSCSI wins, either amend NFR-23 to exempt `fafnir` (naming the compensating control — Synology-side LUN snapshots or more frequent PostgreSQL backups) or require the Synology's own snapshot facility as the substitute.

- **[medium]** FR-9 snapshot rollback does not cover the state that matters most — a Proxmox Guest snapshot captures the Guest's own disk. It does not capture the NFS Home Directory (FR-15) or any Persistent Volume (FR-17) the Guest mutated, because those live on Nidavellir. UJ-6's premise — "makes a change he expects to be destructive, observes the failure mode, and rolls back," costing minutes — is false whenever the destructive change touched shared storage, which is where the operator's actual work lives. This quietly undermines the platform's stated deliverable of fearlessness. *Fix:* add a consequence to FR-9 stating exactly what a snapshot does and does not cover, and add a requirement for a corresponding snapshot facility on Nidavellir-resident data (Synology snapshots on the Home and PV shares) so that "snapshot before change" is a complete operation rather than a partial one.

- **[medium]** Router configuration is load-bearing, outside the Repository, and outside backup — FR-4: "No configuration required to rebuild any component exists only on a running system." FR-12 requires deterministic, recorded, rebuild-surviving addresses. FR-14 forbids Asgard taking over DHCP. The reconciliation is either DHCP reservations on the household router (configuration on a running system, invisible to the Repository, unbacked-up, lost if the router is replaced) or static addressing on every host (which the PRD never says, and which needs a carve-out from the router's DHCP pool — itself a router change). Same problem for the conditional-forward and reverse-delegation needed by FR-11, and for the address pool FR-41 needs to publish Workloads on the LAN. *Fix:* choose static addressing for all Asgard hosts with a reserved range excluded from the router's DHCP pool, record the range and every assignment in the Repository, and add a short "household router configuration" section to the Repository documenting the exact set of manual router changes Asgard depends on — so FR-64's rebuild has them written down.

- **[medium]** S3 precedes S4, guaranteeing UID/GID rework — the skeleton exports a Share and has a Guest consume it before the Directory exists. NFS authorization is by numeric UID/GID (NFSv3) or by idmap domain (NFSv4); files created against local users at S3 will not match Directory-issued IDs at S4, and the Home Directory ownership model has to be redone. Nothing in the skeleton acknowledges this. *Fix:* either fix the Directory's UID/GID range in S1 as a recorded decision so S3 can create the Share with the eventual IDs, or state in S3 that its Share is throwaway and will be re-created after S4.

- **[medium]** The UPS is marked SETTLED in the brief while its gating precondition is still open — the brief's Resolved Foundation Decisions table lists the SMT1500C as a settled choice; the addendum §9 header says "Model - SETTLED"; §11 open question 5 says the unit "must appear on Synology's supported list before purchase," and that failure "forces a topology change rather than a workaround." A decision with an unverified precondition that would restructure FR-57 and FR-58 is not settled. Worse, power continuity is D8 — near the end of the plan — so the topology change would be discovered after nine epics were built assuming it. *Fix:* resolve open question 5 now, before the architecture workflow runs, and if it cannot be resolved, pull the NUT topology decision forward and design for the fallback (a Node as NUT server, with Nidavellir shut down as a client) so D8 is not a re-architecture.

- **[medium]** FR-16's "degrade rather than hang" and NFR-17's "integrity may not be sacrificed" pull in opposite directions — the standard mechanism for preventing uninterruptible-sleep hangs on an NFS outage is `soft` mounts, which return errors mid-operation and can corrupt in-flight writes; `hard,intr` is effectively gone on modern kernels; `autofs` solves mount-on-demand, not a hang after the mount is established. FR-16's consequence "Loss of the Share does not leave processes unkillable in uninterruptible sleep" and NFR-17's "Availability may be sacrificed; integrity may not" cannot both be maximized on the same Share. *Fix:* split the requirement by share class — Home Directories may be soft-mounted (interactive, tolerant of an error) while Persistent Volumes holding durable data must be hard-mounted with the hang accepted — and state that split as a consequence of FR-16 so architecture does not resolve it silently in one direction.

- **[medium]** In-cluster image builds will destabilize etcd, and no requirement prevents it — FR-43 requires image build from committed source inside Asgard, on 4C/8T Zen+ nodes where the addendum already shows 35 vCPU allocated against 32 threads *before* the build runners are counted. etcd is latency-sensitive; sustained CPU contention on a Node hosting a Norn produces leader elections and API latency, which will look like FR-37 failing. NFR-9 bounds memory only — there is no CPU reservation, no requirement that build Workloads be kept off Nodes hosting Control Plane Guests. *Fix:* add an NFR reserving CPU for Control Plane Guests, and a requirement that build Workloads are constrained (CPU limits plus placement away from Norns). Include a build-under-load case in the FR-37 verification.

- **[medium]** No off-site backup, and no acknowledgement that there is none — FR-62 is about surviving loss of *the source system*. Fire, theft, flood, and ransomware take the whole shelf, including Nidavellir and the escrow SSD. The PRD never mentions off-site, never lists it as a non-goal, and never records it as an accepted risk. Given the stated deliverable is "the documentation outlives the hardware," this is a conspicuous omission. *Fix:* add it to §6 as an explicit non-goal with a reason, or add a minimal off-site requirement (encrypted, outbound-only, for the Repository plus the Directory and PostgreSQL dumps — the small, irreplaceable set) since NFR-14 permits outbound traffic.

- **[medium]** A four-node cluster is an even-count quorum with no tiebreaker — FR-6 only requires surviving one Node loss, which 3-of-4 satisfies. But a switch fault or a cabling change producing a 2-2 partition loses quorum on *both* sides, and Proxmox's `/etc/pve` goes read-only cluster-wide. With one unmanaged switch and one uplink, this is a plausible fault, not an exotic one. No QDevice is in scope. *Fix:* either add a QDevice (it can live on Nidavellir, costs nothing, and is instructive — which the brief says is a tiebreaker for design decisions) or record the even-count exposure as an accepted risk in §10 with the read-only-`/etc/pve` recovery Procedure written down.

- **[medium]** NFR-1 is the document's flagship quality attribute and is entirely unfalsifiable — "Every Procedure is executable by the operator six months later with no recall of building it. Ambiguity is a defect." There is no pass/fail procedure, no proxy measure, and the only available tester is the person who wrote it and therefore cannot satisfy the precondition. NFR-2 ("Runbooks state reasoning") and NFR-5 ("the disagreement is a defect to be closed") have the same problem: no detection mechanism. SM-1 measures undocumented steps in exactly one Drill on one Node. The single most-emphasized property of the platform has no test. *Fix:* replace NFR-1's intent with something executable — a cold-execution rule (a Procedure is validated when it is executed without consulting anything outside the Runbook, and the executor records every external lookup as a defect), and a staleness rule (any Procedure not executed in N months is flagged for re-validation). Make the cold-execution record a Repository artifact so SM-1 has more than one data point.

- **[medium]** FR-63's "verified correct, not merely present" has no definition of correct — restores for Guests, Persistent Volumes, PostgreSQL, and Directory data have wildly different correctness criteria (a Guest that boots vs. a Postgres cluster that passes a consistency check vs. a Directory whose entries and group memberships match). "Verified correct" is stated as testable and is not. Same class: FR-44's "A second application repeats the Procedure without variation" and SM-10 — no two real applications have identical ports, claims, and storage, so the requirement is unmeetable as literally worded. FR-3's "The Repository history shows the correction alongside the execution that discovered it" has no definition of "alongside" and no record of executions in git at all. FR-1's "No operational activity is documented in only one form" has no enumerated universe of operational activities to check against. *Fix:* give FR-63 a per-class verification predicate (stated in each restore Procedure and required to be a command with expected output), reword FR-44 to "without editing the Procedure" rather than "without variation," and give FR-1 a Repository-resident register of operational activities so its completeness claim is checkable.

- **[low]** Stale VPN text survives the remote-access cut — §7.2 justifies excluding public DNS and ACME with "an internal authority is sufficient for a **LAN-and-VPN** platform," but remote access was removed from scope entirely. The addendum's `bifrost` registry entry still binds to "Ingress, reverse proxy, **VPN entry**." Minor, but it is evidence the cut was not propagated, which matters when downstream workflows read these documents literally. *Fix:* sweep both documents for VPN references and correct them.

- **[low]** FR-60's "The Drill is repeated after battery replacement" is a year-three obligation stated as an acceptance criterion — it cannot be satisfied at v1 and will sit permanently unchecked, which erodes the meaning of the other consequences. Same class: FR-29's "Renewal failure raises an alert before the certificate expires" cannot be demonstrated without either waiting or forcing a short-lived certificate, and no consequence requires the forcing test. *Fix:* move the battery-replacement drill to a stated recurring obligation (a maintenance Procedure with a trigger) rather than an FR consequence, and add a consequence to FR-29 requiring the renewal-failure alert be proven by deliberately breaking renewal on a test certificate.

- **[low]** The §12 assumptions index is missing its most load-bearing assumptions — it lists six. It omits: where the Repository lives and that it is reachable during rebuild; that the operator's workstation is out of scope; that an alert delivery channel exists at all (§11 Q6 is open and FR-51 depends on it); that DSM supports OIDC well enough for FR-32 (partly covered) *and* that DSM's NUT server can be sequenced last; and that Draupnir's issuance model survives whichever Directory product wins §11 Q1 (FreeIPA bundles the CA, which collapses S4 and S5 into one epic and changes the skeleton). *Fix:* add them, and note explicitly that resolving §11 Q1 in favor of FreeIPA restructures S4/S5 and moves DNS ownership.

- **[low]** NFR-23 encourages snapshots with no retention requirement, on thin pools that corrupt when full — "Snapshot-before-change is available for every Guest, so experimentation is cheap by default" is exactly the behavior that fills an LVM-thin pool, and a full thin pool takes the Guests on that Node with it. There is no snapshot retention, pruning, or capacity alert requirement for Node-local storage — FR-19 covers Nidavellir capacity only. *Fix:* extend FR-19's capacity/alert coverage to Node-local storage, and add a snapshot retention expectation to NFR-23.

- **[low]** Nothing covers the upgrade lifecycle — Proxmox major-version upgrades, k3s version skew, Keycloak's frequent breaking releases (which will break FR-33's client configuration), Directory product upgrades, and base-OS patching are entirely absent from the PRD. FR-1 says "every operational activity" has a Procedure; patching is the most frequent operational activity there is, and the one most likely to be done at 11pm undocumented — which is the exact failure mode §The Problem in the brief exists to prevent. *Fix:* add a Features subsection or at minimum an FR for platform patching and upgrade, with the same dual-form Procedure obligation, and name Keycloak upgrades specifically as a case that requires a snapshot-and-rollback plan.
