# Currency & Reality-Check Review — Architecture Spine, Project Asgard

**Reviewer scope:** verify that every committed decision in `ARCHITECTURE-SPINE.md` (and the versions in `.memlog.md`) was web-researched or reality-checked, not asserted from training data.
**Method:** live web verification against upstream release pages, vendor KBs, official datasheets and issue trackers, August 2026. Every row below was checked against a live source; rows marked "could not verify" were searched for and not confirmed — they are not guesses.
**Date of review:** 2026-08-28.

---

## Verdict

**The Stack table's banner — "Verified current 2026-08-28" — does not hold.** Five of the eleven pinned versions are stale as of the date they claim, and one of those (OpenTofu 1.12.2) sits behind four patch releases including published security advisories. The banner is itself the load-bearing claim under review, and it fails.

The good news is narrower but real: **no second ingress-nginx was found.** Every named component still exists, is still maintained, and none carries a deprecation, archival, EOL or license-change notice. Harbor, Argo CD, Envoy Gateway, csi-driver-nfs, SOPS, age and MetalLB are all demonstrably healthy with releases or commits inside the last eight weeks. OpenBao is real, Linux Foundation–governed, and in production at GitLab and NVIDIA. The EOL sweep that caught ingress-nginx appears to have been done properly.

Where the spine is weakest is not currency but **specificity of behavioural claims**. Two of the six product-behaviour assertions are true as written but materially under-specified in ways that leave a requirement without a supported implementation path (Keycloak `nsAccountLock`) or an invariant without its mandatory precondition (CloudNativePG on local-path). Two hardware claims inherited from the brief are simply wrong.

Recommend: correct the Stack table, add the four missing preconditions, and either drop the "verified current" banner or replace it with a dated, per-row provenance column.

## Findings

- **[critical]** The Stack table's "Verified current 2026-08-28" banner is false — **Five of eleven pinned versions are stale on the very date the banner claims verification: FreeIPA 4.12.5 (upstream is 4.13.3), cert-manager 1.20 (1.21.1), CloudNativePG 1.29.1 (1.30.0), OpenTofu 1.12.2 (1.12.6, with security advisories), Ansible 2.20.5 (2.20.8 / 2.21.x). The banner is exactly the kind of assertion this review exists to catch: it reads as evidence of research while the underlying numbers were not re-checked. Under AD-4 the Repository is the source of truth, and a false provenance line is worse than none. *Fix:* replace the single banner with a per-row `verified` date column and a named source, and re-run the check as a Procedure in the Procedure Index rather than a one-off. Correct the five numbers now.

- **[high]** OpenTofu 1.12.2 is four patches behind and misses published security advisories — **1.12.6 (2026-08-19) carries advisories for OCI-registry credential handling and resource URL resolution. OpenTofu is the tool that holds Proxmox API credentials under the L1 layer, so a credential-handling advisory is directly in scope. *Fix:* pin 1.12.6 (or 1.12.x-latest); note that 1.11.x is now EOL and 1.13.0 is in beta, so 1.12.x is the right line.

- **[high]** AD-2's `nsAccountLock` mapping has no supported implementation, only workarounds — **The spine correctly states that without the mapping "disablement does not propagate and FR-35 is void." What it does not say is that Keycloak ships **no** built-in mapper for this, that the obvious `user-attribute-ldap-mapper` approach produces *inverted* results because `nsAccountLock=TRUE` means disabled, and that upstream issue #21502 has sat open and unassigned since July 2023. FR-35 currently rests on a mechanism that does not exist out of the box. *Fix:* name the actual mechanism in AD-2 — either (a) a custom LDAP mapper SPI jar deployed into Keycloak (community reference: `Nithe14/keycloak-custom-ldap-enabled-mapper`), or (b) an LDAP provider search filter excluding `nsAccountLock=TRUE` combined with `Import Users: Off` so no local copy lingers. Add a Procedure that verifies propagation end-to-end by disabling a test account and confirming token rejection.

- **[high]** CloudNativePG on local-path makes backup a hard prerequisite, and the spine treats it as an ordinary concern — **CNPG endorses local storage for performance, and failover to a *surviving* replica genuinely works. But a local PV pins its pod to one node forever, so CNPG's self-healing (which assumes volumes reattachable on another node) does not apply. When a Node dies, that instance's data is stranded and CNPG rebuilds the standby **from a backup**. The spine's Deferred section says "CloudNativePG failover is the answer; formal HA targets are not set," and the capability map files backup under "Native per system" — neither makes WAL archiving a precondition of the storage choice. *Fix:* state in AD-8 (or a new clause under it) that database instances on local NVMe require configured WAL archiving/`backup` plus ≥3 instances plus pod anti-affinity, and that the deployment is invalid without them. Add the CNPG restore-a-lost-instance drill to the Procedure Index.

- **[high]** "No out-of-band management" is wrong — the Nodes have AMD DASH, with vendor-default credentials — **HP's own white paper lists the EliteDesk 705 G5 Desktop Mini as a DASH-supported Realtek-NIC system: remote power state, boot control, BIOS management, text console redirection and an embedded web UI on ports 623/664, functioning regardless of OS state. The default provisioning account is the vendor default documented in HP's white paper; the literal is omitted here deliberately, as this repository is public. This cuts both ways. It contradicts the brief's constraint (`brief.md:102`) and the addendum's "physical console … is genuinely the floor" (`addendum.md:157`) — there *is* a remote floor below that. And it is an unmanaged, credentialed, out-of-band attack surface sitting on the data switch that AD-4 does not cover and AD-13 does not account for. *Fix:* correct the constraint to "no IPMI/BMC; AMD DASH over the Realtek NIC provides limited OOB power/boot/console." Then decide explicitly: either disable DASH in BIOS on all four Nodes, or bring it under AD-4 as a configuration item with rotated credentials and record it in the address plan.

- **[medium]** cert-manager 1.20 is outside its own stated support window for k3s 1.36 — **cert-manager 1.20 documents support for Kubernetes 1.32–1.35; the spine pairs it with k3s 1.36.4. cert-manager 1.21 (2026-07-08) supports 1.33–1.36. 1.20 also reaches EOL on the release of 1.22, expected ~Nov 2026 — inside this build's likely timeline. *Fix:* pin cert-manager 1.21.x.

- **[medium]** CloudNativePG 1.29.1 is two releases behind — **1.30.0 shipped 2026-06-29 (adds a Lease-based mutex serialising primary promotion — directly relevant to the failover behaviour AD-8 depends on), and 1.29.2 shipped the same day. *Fix:* pin 1.30.x, or 1.29.2 if staying on the 1.29 line; note the promotion-mutex improvement as a reason to prefer 1.30.

- **[medium]** FreeIPA 4.12.5 matches neither upstream nor Rocky Linux 10 — **Upstream is 4.13.3 (2026-08-19); 4.12.5 dates to 2025-09-30. Meanwhile Rocky 10.1 ships the 4.12 line, reported in the wild as **4.12.2**. Under AD-17 the Directory is installed from the distro AppStream, so the version is whatever Rocky ships — pinning a specific upstream patch number that the distro does not carry is a claim the build cannot satisfy. *Fix:* record the version as "FreeIPA 4.12.x, as shipped by Rocky Linux 10 AppStream" and drop the false patch precision, or verify the exact `ipa-server` NEVRA on the target Rocky minor release and pin that. Also confirm which Rocky 10 minor is current — sources conflicted between 10.1 and 10.2, and I **could not verify** which is shipping today.

- **[medium]** "Ansible 2.20.5" is stale and conflates two version namespaces — **ansible-core 2.20.8 is the latest 2.20 patch and 2.21.x is the current series; 2.20.5 dates to 2026-04-21. Separately, "Ansible 2.20.5" is an ansible-core number, while the thing an operator installs is usually the community package (Ansible 13.x). *Fix:* state both explicitly, e.g. "ansible-core 2.21.x (community package Ansible 14.x)", and say which one the Automation pins.

- **[medium]** The DS925+ has no third-party drives on its compatibility list — the WD Red Pro is permitted, not listed — **The DSM 7.3 reversal is real and does allow the WD Red Pro 14 TB to create pools. But the live DS925+ HCL contains 41 entries, all Synology HAT/SAT; zero WD. The drives are *unlisted-but-permitted*, which is a materially different support posture from *validated* — and it is the posture that a future DSM release could narrow again, as the 2025 policy already demonstrated. Given AD-8 puts all bulk storage and all backups on this one array with no independent second target (the spine's own "largest accepted risk"), that dependency deserves naming. *Fix:* correct any "on the compatibility list" phrasing in the brief/addendum to "permitted as unlisted under the DSM 7.3+ policy"; add a note that DSM major-version upgrades on Nidavellir are a change requiring a compatibility re-check, not routine patching.

- **[medium]** The Deferred "NVMe tier on Nidavellir" is only reachable with Synology-branded SSDs — **The DSM 7.3 third-party relaxation covers 3.5" HDD and 2.5" SATA SSD only. Unlisted M.2 NVMe remain unsupported for storage pool creation *and* cache creation on 2025 DS Plus models; the DS925+ M.2 HCL has 7 entries, all Synology SNV3400/3410/5420. The Deferred item reads as an open, cheap option; it is actually gated on buying Synology NVMe at Synology prices. *Fix:* add the constraint to the Deferred entry so the future decision is costed honestly. Also update the memlog's "DSM 7.2+" reference — current DSM is 7.4.1 (2026-07-23).

- **[medium]** synology-csi is the one real bus-factor risk in the stack — **Not EOL, not deprecated, but ~1–2 releases per year from a single vendor with single-digit committers, and the README claims only "DSM 7.0 or above" — explicit DSM 7.3/7.4 validation **could not be verified**. Note that **v1.3.1 (2026-08-05) is a security-relevant release**: it enables DSM HTTPS certificate verification by default, closing a credential-exposure path. *Fix:* pin ≥v1.3.1 explicitly rather than "current". Since it backs only the second (ReadWriteOnce) storage class under AD-8 and csi-driver-nfs is the default, record the fallback plainly: if synology-csi stalls, the iSCSI class is dropped and its volumes move to NFS — semantics lost, no data lost.

- **[medium]** Six Stack rows carry no version at all, which conflicts with AD-4 — **Envoy Gateway, Argo CD, Harbor, csi-driver-nfs, synology-csi and SOPS+age are all listed as "current" or "Gateway API". All six are healthy, so this is not a currency risk — it is a reproducibility one. AD-4 says no configuration required to rebuild a component exists solely on a running system, and "current" resolves differently on every rebuild. Two of these have real upgrade hazards that a floating pin would walk into blind: Envoy Gateway 1.9 requires Gateway API CRDs to be updated to **v1.6.1 before upgrade**, and Harbor 2.15.2 **auto-migrates its bundled PostgreSQL 15 → 18 via `pg_upgrade` on container start**. *Fix:* pin all six (Envoy Gateway 1.9.1, Argo CD 3.5.2, Harbor 2.15.2, csi-driver-nfs 4.13.4, synology-csi 1.3.1, SOPS 3.13.3 + age 1.3.1) and note the two upgrade hazards.

- **[medium]** DSM admin login under OIDC is unverified, and AD-9's break-glass does not cover the NAS console — **DSM's generic OIDC profile is confirmed and does permit local users to sign in via SSO. What official documentation does **not** settle is whether the built-in `admin` account or administrators group is excluded from SSO, or whether a local-password fallback for DSM admin is guaranteed. AD-9 requires break-glass independent of the Directory, and Nidavellir is the single storage point of failure — a DSM admin lockout during an IdP outage is precisely the scenario AD-9 exists for. *Fix:* treat this as a build-time gate, not a design assumption: validate on hardware before enabling DSM SSO, and record the verified answer in the Repository. Keep a local DSM administrator with an escrowed credential regardless.

- **[low]** AD-10's "real ceiling" for the hypervisor UI now has a number — record it — **AD-10 requires parties that cannot honour 15 minutes to declare their real ceiling and calls an unrecorded bound a defect. The Proxmox number is verified: **2 hours**, and the ticket is refreshable by presenting the old one to `/access/ticket`, so the effective ceiling is 2h from last activity rather than 2h from login. Proxmox staff confirmed in April 2026 that neither back-channel nor RP-initiated logout is implemented. *Fix:* write "2 hours, sliding on refresh; no back-channel or RP-initiated logout (vendor-confirmed 2026-04)" into the per-Relying-Party table.

- **[low]** The APC SMT1500C is rated 1440 VA, not 1500 VA — **Schneider's official datasheet gives 1000 W / 1440 VA; "1500VA" is the model name. The 1000 W figure the load math actually uses (~320 W, ~3.1× headroom) is correct, so nothing in AD-11 changes. *Fix:* correct the number in the brief and addendum for accuracy. Confirmed alongside: 8 × NEMA 5-15R with no surge-only group, USB present, NUT drives it via `usbhid-ups`.

- **[low]** DSM's NUT server has a 5-client UI cap and SSH-only credentials — both touch AD-4 and AD-11 — **"Enable network UPS server" is confirmed and it is stock NUT `upsd`, so any NUT client connects (the Synology-worded UI is not a technical restriction — good news for the four Nodes). But the web UI caps the permitted-IP list at **5 entries**: four Nodes fits with exactly one spare, and a fifth client requires SSH. Worse for AD-4: the NUT identity (`ups`/`monuser`/`secret`) lives in `/usr/syno/etc/ups/upsd.users` and can only be changed over SSH, where DSM upgrades may revert it. That is configuration existing solely on a running system. *Fix:* note the 5-entry ceiling in AD-11's client budget; add a post-DSM-upgrade verification step to the UPS Procedure that re-checks the NUT credentials and permitted-client list, and treat the drill-measured margin as invalid until it passes.

- **[low]** The CI decision should name Autoscaling Runner Sets, not "Actions Runner Controller" — **Legacy community ARC was formally deprecated with ARC 0.14.0 (2026-03-19); GitHub supports only the Autoscaling Runner Sets architecture, with legacy on community support in the same repository.
