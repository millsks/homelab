# Rubric Walker Review — ARCHITECTURE-SPINE.md (Project Asgard)

Lens: the good-spine checklist from `references/reviewer-gate.md`, read against the skill's Overview definition of spine (invariants vs. seed) and the driving PRD.

Reviewed: `_bmad-output/planning-artifacts/architecture/architecture-homelab-2026-08-28/ARCHITECTURE-SPINE.md` (status: draft), its `.memlog.md`, and `_bmad-output/planning-artifacts/prds/prd-homelab-2026-08-28/prd.md`.

## Overall Verdict

**Changes required — not a rewrite.** Where this spine decides, it decides unusually well: AD-18's four-part placement test, AD-10's per-relying-party revocation bounds, AD-11's *measured, recorded* shutdown margin, and AD-9's catch that a Break-glass home nested under an NFS mount point is shadowed are all sharper than the norm, and the stratified-layer paradigm with AD-1 as its single enforceable claim genuinely earns its keep. The spine also holds the right altitude and is close to correctly terse.

It fails on **breadth and on enforcement mechanism**. Four dimensions this altitude owns are silent or near-silent — capacity management, upgrade/patching lifecycle, backup/restore, and change-safety/rollback — and one of them (backup) had a real decision in the memlog that did not survive distillation. Separately, a recurring pattern: several Rules state a *prohibition* ("is prohibited", "must not", "are not used") without naming the configuration or check that makes the prohibition detectable, which is precisely the aspirational-Rule failure the checklist targets. And a genuine structural hole sits between the two declarative tools: nothing owns the Proxmox host OS, the NAS, or the network devices, while AD-4 and FR-7/FR-64 assume everything is rebuildable from the Repository.

Fix the four criticals and the enforcement-mechanism highs and this becomes a strong build substrate.

**Findings: 4 critical · 8 high · 11 medium · 8 low (31 total)**

## Critical

- **[critical]** Capacity management is a wholly silent dimension (whole spine / NFR-6, NFR-7, NFR-9) — the PRD makes capacity a two-sided, explicitly anti-gameable constraint (≤90 GB committed Guest memory *and* ≥15 GB schedulable inside Yggdrasil, every Guest declaring explicit limits), and NFR-7's single-Node-loss survival is derived from it. The spine contains no AD, no Consistency Convention row, and no Capability-Map row for capacity. Worse, AD-18 actively spends the budget — "a service runs inside Yggdrasil by default" — with no ceiling attached, so each epic that adds a service (D5 `fafnir`, D6 observability, D7 `andvari`, D4 `sindri` + runners) consumes headroom independently and none of them can see the total. This is the textbook divergence the spine exists to prevent. *Fix:* add an AD binding capacity: every Guest declares an explicit memory limit; the committed-memory total is a recorded number in the Repository updated in the same change that adds a Guest or Workload (mirroring AD-16's "add the name in the same change" pattern); adding a service that would breach 90 GB committed or drop schedulable headroom below 15 GB requires removing something, and Harbor is the named first cut per the memlog. Add a "Capacity (NFR-6–9)" row to the Capability Map.

- **[critical]** Upgrade, patching, and version lifecycle is a wholly silent dimension (whole spine / Stack) — nothing states how any component is patched, how versions are pinned, or in what order the layers upgrade. This is not a minor omission for this design: the paradigm is strictly layered, so upgrade ordering is a *derived invariant* (you cannot upgrade k3s before the Directory it authenticates against, or move Proxmox before the Guests it hosts), and AD-17's mixed-OS estate doubles the patch surface. The operator has already been bitten by lifecycle once — the memlog records ingress-nginx reaching EOL mid-design and forcing the Envoy Gateway reversal — which makes the absence of any component-currency rule the more striking. *Fix:* add an AD: every component version is pinned in the Repository and upgraded by a commit, never in place; upgrades proceed bottom-up through the layers, with a Guest snapshot (NFR-23) taken first; each component's upstream support horizon is recorded and reviewed on a stated cadence, so an EOL is found before it is exploited.

- **[critical]** Backup and restore has no invariant at all despite being a full PRD capability area (Capability Map / FR-61–64, NFR-18, SM-5, epic D9) — the map's row reads "Backup and recovery (FR-61–64) | Native per system | AD-4, AD-8", but neither AD-4 nor AD-8 says a word about backup, so the row cites governance that does not exist. The memlog holds a real, load-bearing decision here (line 37: native mechanisms only — Synology Btrfs snapshots + Hyper Backup, Proxmox vzdump, CloudNativePG barman; **Velero deliberately not introduced**; plus the encrypted critical subset to the SanDisk), and none of it reached the spine. Two epics building independently will diverge exactly here — D9 introduces Velero as the "Kubernetes-native" answer while D5 relies on barman — and NFR-18's "configured-but-untested is treated as not present" has no binding expression either. *Fix:* promote the memlog decision to an AD: each system is backed up by its own native mechanism and no cross-cutting backup abstraction is introduced; every backed-up class has an executed restore on record before the class is considered protected; the encrypted critical subset (Directory data, PostgreSQL dumps, CA root key, Break-glass escrow) lives off-platform. Then re-point the Capability Map row at it.

- **[critical]** The declarative-ownership boundary leaves the host OS, the NAS, and the network devices unowned (Consistency Conventions / FR-7, FR-64, AD-4) — the convention reads "OpenTofu owns Proxmox resources; Ansible owns in-guest configuration; the boundary is the guest's first boot." That partitions the world into two zones and omits three populated ones. Nothing owns **the Proxmox host itself** — yet AD-7's interface assignment, AD-6's time client, AD-9's Break-glass account, and AD-5's ACME certificate all land on the Node, and FR-7 demands a Node be rebuildable from the Repository. Nothing owns **Nidavellir** — shares, exports, iSCSI LUNs, the NUT server, snapshot and Hyper Backup schedules — despite it being the most configuration-bearing device in the estate and the subject of AD-8 and AD-11. And AD-4 asserts "managed network devices are configuration items under this rule, not exceptions" while naming no tool that manages them and the Deferred section describing the switches as unmanaged. *Fix:* extend the convention to name an owner for every configuration-bearing surface — Ansible owns Node (hypervisor host) configuration as well as in-guest, with the manual ISO install bounded to a Runbook; name the mechanism for DSM (Ansible against the DSM API, or an explicitly Runbook-only surface with its settings exported to the Repository and diffed); and either name a tool for the network devices or drop AD-4's claim over them and record it as a stated exception.

## High

- **[high]** AD-4's reconciliation clause is false for L0–L2, and the paradigm overclaims with it (AD-4 / Design Paradigm) — the paradigm states every layer is "reconciled toward, never applied imperatively", and AD-4's Rule says direct changes "are reverted by the next reconciliation." That holds only for L3–L5 under Argo CD, and only if Argo is configured with self-heal and prune — which nothing requires. For L0–L2 there is no reconciliation loop at all: OpenTofu and Ansible are push-based and run when the operator runs them, so a manual change to Proxmox, FreeIPA, or the NAS is never reverted and never even *noticed*. The Rule as written cannot be enforced across two thirds of the layers. *Fix:* split the Rule. For the GitOps layers, require self-heal and prune enabled (that is the enforcing configuration). For the push-based layers, require a scheduled check-mode/plan run that reports drift as an alert — drift detection is what makes "the Repository is the sole source of truth" checkable rather than aspirational.

- **[high]** No invariant binds fault-domain placement, on which the entire reliability posture rests (missing AD / FR-25, FR-37, FR-38, NFR-7, NFR-16) — NFR-16 requires identity, storage, and cluster control to tolerate loss of one Node *without operator intervention*, and FR-38 explicitly requires Control Plane Guests distributed across Nodes. The spine expresses this only as decorative text inside a seed diagram ("mimir + replica", "urd · verdandi · skuld, one per Node"). Seed is owned by the code once it exists; an invariant is not. D2 (Directory replica), D3 (three control planes) and D5 (CloudNativePG instances) are separate epics that will each decide placement independently, and nothing stops both `mimir` Guests landing on `odin`. *Fix:* add an AD — no two instances of any replicated component share a Node; placement is declared, not scheduled by convenience; a change that would co-locate replicas is a defect. Cover Proxmox Guest placement and Kubernetes anti-affinity in the one rule.

- **[high]** NFS mount semantics are undecided, and FR-16 and NFR-17 pull in opposite directions over a USB-attached NIC (missing AD / FR-16, NFR-17, AD-8, AD-9) — FR-16 requires storage unavailability to *degrade rather than hang*; NFR-17 says availability may be sacrificed but integrity may not. Those resolve to opposite mount options: soft mounts satisfy FR-16 and risk silent corruption of in-flight writes; hard mounts satisfy NFR-17 and hang the host. The choice is sharpened by AD-7, which puts all storage traffic on an adapter the spine itself describes as resetting and renumbering. AD-9 gestures at "an automounter" in passing, which is the right family of answer but is stated as an aside inside a Break-glass rule rather than as the storage invariant it is. This is a real trade-off, non-obvious, and two epics (D1 storage depth, S3 first Share) would choose incompatibly — the spine's own inclusion test, passed on all three counts. *Fix:* add an AD fixing mount semantics per volume class: automounted, hard, with `intr`/timeout bounds for interactive and home-directory paths (bounded hang, no corruption), and state explicitly that no Workload volume carrying unreplayable writes is served over NFS. Cross-reference AD-8's placement classes.

- **[high]** Four Stack rows are unpinned and one carries a non-version, including the component chosen *because* of a lifecycle failure (Stack) — the table is headed "Verified current 2026-08-28", yet Argo CD, Harbor, `csi-driver-nfs`/`synology-csi`, and SOPS+age all read "current", MetalLB reads "0.16.x" (a range, not a pin), and **Envoy Gateway's version cell contains "Gateway API"** — a protocol name in a version column, so the one component adopted in direct response to the ingress-nginx EOL is the one whose version was never recorded. "Current" is unverifiable six months from now, which is exactly NFR-1's standard. The deterministic `lint_spine.py` pass flags unpinned Stack versions; these will trip it. *Fix:* pin every row to a verified version as of the stated date, including Envoy Gateway; where a version genuinely cannot be fixed yet, move the row to an Open Questions section with a "verify at build time" marker rather than writing "current".

- **[high]** The runtime secret store is absent from the spine entirely, though it is a decided component (Stack / AD-15, FR-54, epic D7) — the memlog carries a two-stage decision: SOPS+age from S1, then a runtime store as `andvari` with External Secrets Operator, with OpenBao as the default candidate since Vault relicensed to BSL, "confirm at build time." The spine's Stack lists SOPS+age and nothing else; `andvari` appears in the placement table and diagrams as an unnamed "secret store"; AD-15 says only that "Workload secrets are delivered at runtime" without naming the delivery mechanism. Delivery mechanism is a genuine divergence point — ESO vs. the Secrets Store CSI driver vs. sealed-secrets vs. Argo plugins are mutually incompatible integration patterns — and D7 has no guidance. *Fix:* name the delivery mechanism in AD-15 (ESO reconciling from the store into Kubernetes Secrets) and add the store product to the Stack, or record it as an explicit open question with the BSL context; do not let a decided item vanish between memlog and spine.

- **[high]** Change-safety and rollback have no invariant (missing AD / FR-9, FR-45, NFR-23) — FR-45 requires deployments be rollbackable, FR-9 requires Guest snapshot and rollback, and NFR-23 requires snapshot-before-change to be *available for every Guest so experimentation is cheap by default*, which is close to the platform's stated reason for existing. The spine says nothing. Rollback is a classic divergence: revert-the-commit, Argo history rollback, Helm rollback, and VM snapshot restore are four different mechanisms with four different blast radii, and D3/D4/D5 would each pick one. *Fix:* add an AD — for Workloads, rollback is reverting the commit and letting reconciliation converge (no imperative rollback, consistent with AD-4); for Guests, the pre-change snapshot is the rollback path and taking one is a required step in any Procedure that mutates a Guest, with a stated retention bound so snapshots do not consume the capacity NFR-6 protects.

- **[high]** AD-7 makes the membership switch an unmitigated single point of failure and forecloses the standard remedy (AD-7 / FR-6, NFR-16) — the Rule mandates one isolated membership switch with no uplink and adds "membership never traverses the USB-attached adapter," which is a well-reasoned prohibition against a *primary* ring on a resetting NIC but reads as absolute. The consequence: the membership switch fails and all four Nodes lose cluster membership simultaneously, and corosync's built-in remedy — a lower-priority second knet link that carries nothing until the first fails — is prohibited by the Rule's own wording. Compounding it, four Nodes give an even quorum profile with no QDevice named anywhere in the spine. Neither the switch SPOF nor the quorum arithmetic appears under Deferred as an accepted risk. *Fix:* narrow AD-7 to say the *primary* membership link never traverses the added adapter, explicitly permitting a lower-priority fallback link on the data switch; and either name a QDevice or record the four-node quorum profile and the membership-switch SPOF as accepted risks under Deferred.

- **[high]** The spine has no Open Questions section, so unresolved items have nowhere to live (whole spine) — the skill requires every dimension the altitude owns to be *decided, deferred, or an open question*, but the document offers only Decided (ADs, Conventions, Stack) and Deferred. Deferred means "we chose not to decide this"; it is the wrong home for "this is not yet known." Real unresolved items consequently either vanished (the secret-store product, per the finding above), got recorded as fact ("current" versions), or sit only in the memlog (the DMS heartbeat's origin; the M.2 question, which at least made Deferred). *Fix:* add an `## Open Questions` section with a revisit condition per item, and move the genuinely-unknown-at-draft-time items into it.

## Medium

- **[medium]** AD-2's prohibition names no enforcing configuration (AD-2 / FR-30) — "Creating an Account directly in the IdP is prohibited" is a policy statement, not a checkable rule; a solo operator under time pressure will create a local Keycloak user during an outage and the spine has no way to detect it. The enforcing mechanism exists and is one setting: the user-federation edit mode is read-only and local account creation and self-registration are disabled in the realm. *Fix:* state the configuration in the Rule, so the prohibition is verified by inspecting the realm rather than by the operator's memory. Same treatment for "The IdP must be rebuildable without loss of identity data" — name the drill that proves it, or it is an assertion.

- **[medium]** AD-8's placement rule is defeated by its own default (AD-8 / FR-18, FR-46) — the Rule prohibits database-class random I/O on Nidavellir while simultaneously making NFS the *default* storage class. A Workload or Helm chart that does not name a class lands on spinning disks by default, which is exactly the failure the AD exists to prevent, and "database-class random I/O" is a judgment call with no test attached — a striking contrast with AD-18, which supplies a four-part test for the analogous placement question. *Fix:* give AD-8 a test in AD-18's style (does it perform random writes to a durable store? does it hold a WAL or transaction log?), and require every PersistentVolumeClaim to name its class explicitly so nothing reaches HDD by omission.

- **[medium]** AD-14 declares part of its own Rule unenforceable without offering the enforceable substitute (AD-14 / FR-34) — "bypass prevention is convention, not network enforcement, because the flat LAN forecloses the segmentation that would enforce it" is honest, and the Deferred section backs it up, but it leaves an AD carrying an aspirational clause when a checkable one is available at this altitude. *Fix:* replace the convention with a structural rule that does not need network segmentation: a Workload fronted by an authenticating proxy is exposed only through that proxy's route, no HTTPRoute may target the backend Service directly, and the backend Service is ClusterIP-only. That is inspectable in the Repository — which is the whole point of AD-4.

- **[medium]** AD-16 makes an out-of-Repository document authoritative, contradicting AD-4 (AD-16 vs. AD-4) — the Rule says every name comes from "the registry in the brief addendum, which is authoritative," while AD-4 says no configuration required to rebuild any component may exist outside the Repository. The naming registry is rebuild-required configuration (AD-16 itself binds FR-11/FR-12 addressing and naming) sitting in a planning artifact. *Fix:* move the registry into the Repository as the authoritative copy and cite the addendum as its origin, not its home.

- **[medium]** Nothing mandates certificate-expiry monitoring, which is the PRD's named silent-failure risk (AD-5, AD-12 / FR-29, PRD §10 and OQ 6) — AD-5 correctly requires the Directory CA renewal role's location, health check, and relocation Procedure be *named in the Repository*, which closes the placement half of open question 6. It does not close the detection half: a named health check that nothing runs or alerts on does not prevent the failure mode the PRD describes — the Directory's own certificates expiring silently, well after the fault. *Fix:* add an explicit clause (in AD-5 or AD-12) that certificate expiry across every issuing path is monitored and alerts before expiry, with a stated lead time.

- **[medium]** NFR-11's plaintext-HTTP prohibition and its named exclusion list did not survive into the spine (Consistency Conventions / NFR-11) — the PRD carefully enumerates what is deliberately *not* covered by Draupnir certificates (SSH host keys, NFS on the trusted LAN, authenticated-but-unencrypted Redis, cluster membership traffic) and notes a blanket "all traffic" claim would be false. The spine's certificates convention reads only "ACME only; no manual installation, no self-signed certificate outside the platform chain." The exclusion list is precisely the sort of thing that prevents a later argument ("must Redis be TLS?") and it is gone. *Fix:* carry both halves into the certificates convention — no endpoint served over plaintext HTTP, and the four named exclusions as a closed list.

- **[medium]** AD-3 provides no check that the Procedure Index is complete or that both forms exist (AD-3 / FR-1, SM-1) — the convergence test (Automation reports zero changes against a hand-built system) is excellent and genuinely enforceable. The surrounding claims are not: nothing detects a Procedure that exists but was never indexed, or an Index entry whose Automation was never written. Since the Index is declared "the authoritative enumeration of every operational activity," an unnoticed omission silently narrows what SM-1 and D11 test. *Fix:* add a repository check — every Index entry resolves to both an existing Runbook and existing Automation, and every Runbook file appears in the Index. That makes the dual-form contract mechanically true rather than diligently maintained.

- **[medium]** A Deferred item leaves a live divergence open (Deferred — PostgreSQL) — "PostgreSQL beyond operator-managed replication. CloudNativePG failover is the answer; formal HA targets are not set." Deferring the *target* is fine; what is left open is the *shape* — instance count, synchronous vs. asynchronous replication, and whether the standby is even in the D5 scope. D5 could deliver a single instance and still claim conformance, which would quietly void the NFR-16 posture and the memlog's stated reason for reversing PostgreSQL out of a VM in the first place ("survives Node loss via CNPG-managed streaming replication with automatic failover"). Also note "operator-managed" is ambiguous between the Kubernetes operator and the human. *Fix:* state the minimum shape (instance count ≥2 on distinct Nodes, replication mode named) as decided, and defer only the availability target.

- **[medium]** AD-11's re-measurement trigger is too narrow (AD-11 / FR-57, FR-60, NFR-22) — the margin is re-measured "after battery replacement," but the measured quantity is the *duration of the shutdown sequence*, which changes whenever the set of things being shut down changes. NFR-22 anticipates Nodes, Guests, and Workloads being added routinely; each addition lengthens the sequence against a fixed battery, and nothing requires re-measuring. *Fix:* add the second trigger — the margin is re-measured after battery replacement **and** after any change to the set of participants in the Shutdown Sequence, as a required step in the add-a-Node/Guest Procedure.

- **[medium]** The frontmatter overclaims NFR coverage that the Capability Map does not deliver (frontmatter `binds` / Capability → Architecture Map) — `binds: [FR-1..FR-65, NFR-1..NFR-23, S1-S7, D1-D11]` asserts complete coverage, but the map is organized entirely by FR range and has no NFR dimension; NFR-6, 7, 9 (capacity), 17 (integrity), 18 (proven recovery), 20, 21, 22, 23 have no governing AD and no map row. The claim reads as coverage where the criticals above show gaps. *Fix:* add an NFR column or rows to the map, and narrow `binds` to what is genuinely bound.

- **[medium]** The PRD's sanctioned thin forms violate spine conventions with no rule for recording a temporary deviation (whole spine / PRD §9, epics S5 and S7) — the delivery plan explicitly permits the IdP on an embedded database through S5, and a hand-built, hand-pushed image through S7, each paired with the deepen epic that retires it. Both breach spine conventions as written (Images "built from committed source... pulled from the internal registry"; the AD-8 placement rule). The spine, read alone by an agent building S7, forbids what the PRD mandates — and nothing requires a deviation to carry the epic that retires it, which is exactly how a thin form becomes permanent. *Fix:* add a convention row: a sanctioned deviation from an AD is recorded in the Repository with the epic that retires it and a verification that fires if it outlives that epic.

- **[medium]** Observability retention is a one-line convention with no bound and no link to capacity (Consistency Conventions / NFR-8, PRD §10 risk) — "Logging | Shipped to the central store; retention bounded and stated (NFR-8)" states that a bound exists without stating one, and metrics retention is not mentioned at all. The PRD lists capacity exhaustion from observability retention as a named risk. A convention that says "a number exists" is not enforceable in the way AD-11's "recorded as a number in the Repository" is. *Fix:* apply AD-11's pattern — retention for metrics and logs is a number recorded in the Repository, and the resulting storage ceiling counts against the capacity budget from the capacity AD.

## Low

- **[low]** Rationale is bleeding into Rules where the memlog is its home (AD-6, AD-7, AD-9, AD-12 / skill Overview) — the spine is otherwise commendably terse, but several Rules end in a *because*: AD-6's "Kerberos tolerates roughly five minutes of skew, and the uplink is a wireless bridge"; AD-7's "USB Ethernet resets and renumbers, which is tolerable for traffic that retries and intolerable for the signalling that decides whether a Node is alive"; AD-9's "local alone is insufficient, since a home nested under the Share's mount point is shadowed while mounted"; AD-12's "because the household router is beyond the UPS's reach." All four are already in the memlog. *Fix:* cut them. (AD-9's is the one worth arguing to keep — the *because* is the non-obvious part a future builder would otherwise undo — but if kept it should be a parenthetical, not a clause of the Rule.)

- **[low]** The paradigm section carries a narrative sentence (Design Paradigm) — "The upward-dependency prohibition is the paradigm's single enforceable claim; every circular-dependency failure this design eliminates is an instance of it" is commentary about the spine rather than an invariant of the system, and AD-1 already states the rule. *Fix:* delete; it belongs in the memlog or a rendering.

- **[low]** The paradigm table's "Realm" column contradicts AD-16 (Design Paradigm table vs. AD-16) — AD-16 rules that "Realms name tiers; beings name instances," yet the table's Realm column lists `mimir`, `draupnir`, `forseti`, `fafnir` — beings — alongside `asgard` and `yggdrasil`, which are realms. The one AD about naming is contradicted by the first table in the document. *Fix:* rename the column to "Named components", or list only the realms.

- **[low]** AD-15's commit-time check is bypassable and has no second line (AD-15 / NFR-10) — "A commit-time check prevents plaintext" almost certainly means a pre-commit hook, which `--no-verify` defeats, and NFR-10 extends to *history*, which a local hook cannot police. *Fix:* require the check at both commit time and in CI on the pushed branch, so the guarantee does not rest on the hook the operator can skip.

- **[low]** The k3s datastore is never named (Stack / FR-37) — FR-37 requires surviving loss of one Control Plane Guest, which implies embedded etcd with three servers rather than the single-server SQLite default, and etcd's disk placement matters (AD-8's local-NVMe rule covers it only implicitly, via Guest root disks). Cheap to state, and it removes an assumption from S6/D3. *Fix:* name embedded etcd and its disk class in the Stack or in AD-8's placement list.

- **[low]** The dead-man's-switch heartbeat has no named origin (AD-12 / FR-51) — AD-12 makes the heartbeat load-bearing (the memlog is emphatic: with the router off-UPS it is the only path surviving a whole-house outage), but never says what emits it. The choice matters and is an AD-1-flavored placement decision: emitted from inside Yggdrasil, routine cluster maintenance pages the operator; emitted from Nidavellir, it covers more failure modes. *Fix:* name the emitter, and record it as an AD-18 placement-table row.

- **[low]** AD-17 states a defect condition with no verification mechanism (AD-17 / FR-7) — "A role that assumes one family is defective" is the right rule, but nothing exercises roles against both families, so the defect is found at 2 a.m. during a rebuild rather than in CI. The `brokkr` runners already exist to run it. *Fix:* require each role to be exercised against both OS families in CI before it is considered complete.

- **[low]** AD-7 depends on hardware the PRD lists as an optional purchase, with no degraded configuration stated (AD-7 / FR-65, PRD §7.2) — the PRD's out-of-scope list reads "Additional hardware — beyond the UPS and, **optionally**, 2.5 GbE adapters," while AD-7 mandates the added adapter for all storage, Workload, backup, and outbound traffic. If the adapters are not bought, a single-NIC Node cannot satisfy AD-7 at all, and the rule offers no fallback. *Fix:* state the adapters as a prerequisite of AD-7 (removing "optional" upstream), or name the degraded single-NIC configuration and what it costs.

- **[low]** Two operability NFRs have no representation (NFR-20, NFR-21) — "the operator can determine current platform state from the Repository and the observability system without logging into individual hosts" and "routine operations require no Break-glass credential" are both real design constraints (the first shapes what observability must expose; the second shapes AD-9's scope, which currently defines Break-glass without saying it is emergency-only). *Fix:* fold NFR-21 into AD-9's Rule as a one-clause scope statement, and NFR-20 into the observability/Capability Map coverage added for the criticals.

## What the spine gets right (kept deliberately short)

AD-18 is the strongest artifact in the document — a default plus a four-part escape test plus a table recording which test each service met, which is exactly how you stop the next service being argued from scratch; its self-declared registry caveat with a bounded mitigation and a verifying Procedure is model-grade honesty. AD-10's "an unrecorded bound is a defect" and AD-11's "measured by Drill and recorded as a number, never estimated" convert soft claims into checkable ones. AD-9's home-directory-outside-NFS catch is the kind of non-obvious call that justifies a spine existing. AD-1 is a genuine paradigm-level invariant rather than a restated preference. Where this review pushes hardest — enforcement mechanism, and dimensions left silent — it is asking the rest of the document to reach the standard these already set.
