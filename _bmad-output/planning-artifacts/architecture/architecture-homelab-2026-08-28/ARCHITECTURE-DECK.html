Project Asgard

Four mini PCs, a NAS and a UPS, assembled into a private cloud that behaves like a corporate environment rather than a pile of self-hosted containers.

Everything here follows from one rule: no layer may require a higher layer in order to start or to authenticate.

01 · The stack

Six layers, and one test for where anything goes

Services run inside the cluster by default. A service moves out only if it meets a named test — the cluster needs it to start or authenticate, a lower layer depends on it across cluster loss, it needs host-level identity a pod can't give, or recovery requires it. Applied across the platform, exactly two services qualify.

02 · Topology

Two traffic classes that never share a wire

Each node is dual-homed. The counterintuitive part: the faster link carries bulk traffic and the slower one carries heartbeats.

03 · Identity

One account, two protocols, one revocation

The directory is the only account store. The identity provider federates to it and holds sessions and clients — never identity — so it can be rebuilt without loss.

04 · Failure modes

What breaks when something dies

The most useful view for whoever is reading this mid-incident. Choose a component.

05 · Reversals

Four decisions that changed, and why

Each was driven by a finding rather than a preference. They are recorded because the reasoning matters more than the outcome.

06 · Build order

A walking skeleton, then depth

A thin vertical slice first, exercising every integration seam while each is still cheap to change — because integration seams are where this class of build fails. Nothing in the skeleton is redundant or complete.
