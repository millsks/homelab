# Adversarial Review — ARCHITECTURE-SPINE.md

## Verdict

The spine is strong where it was fought over and thin where it was merely written down. AD-1, AD-7, AD-9, AD-10, AD-11 and AD-18 are genuine invariants: each names a failure mode, states a rule with a sharp edge, and would actually stop a builder mid-mistake. But the spine governs *choices already argued* and leaves *consequences not yet met* unowned, and that is where two obedient builders diverge. Three structural problems dominate. First, the paradigm's "single enforceable claim" — no upward dependency — is enforced by AD-1 only *into Yggdrasil*, while the L1→L2 direction (Nodes taking time from AD-6, identity from AD-2, certificates from AD-5) is a textbook upward dependency the spine's own layer table forbids and no AD catches; the layering is descriptive at L1/L2 and prescriptive only at L3/L4, and builders will read whichever half suits them. Second, roughly a third of the ADs govern *media* rather than *multiplicity or ownership*: AD-8 says where database bytes land but not how many database clusters exist; AD-15 says no plaintext reaches the Repository but not that every secret must reach it; AD-14 says Gateway API but not how many Gateways; AD-12 says a dead-man's switch exists but not that there is exactly one. Every one of those is a two-compliant-builders hole. Third, the artifacts that make rebuild possible are unnamed: OpenTofu state, the age private key, the FreeIPA POSIX ID range, and the enumerated backup-coverage map are each load-bearing for FR-64 and each absent from the spine, so AD-9's escrow list is provably insufficient to rebuild the platform it exists to rebuild. Two ADs are also currently unsatisfiable as written — AD-3's dual form against an easy-managed switch, and AD-3's convergence test against OpenTofu — and an unsatisfiable AD trains builders to treat ADs as advisory. Recommendation: the spine needs an ownership pass (one owner per shared entity), a cardinality pass (how many of each thing), and a bootstrap pass (what must exist before the layer below it can be built), plus AD-19 through roughly AD-27 below. It should not go to epic decomposition until at least the seven critical findings are closed, because each of them is a decision two epics will otherwise make differently and discover in integration.

## Findings

### Critical

- **[critical]** The layer model inverts at L1/L2 and only AD-1 notices, in one direction (layering) — Unit A is the Node-build Procedure `l1-hypervisor/runbooks/host-build-debian.md` + `ansible/roles/node_base`, written by the S2 epic: it enrolls each Node in FreeIPA (FR-20 "any Node or Guest"), points chrony solely at `mimir` (AD-6: "no host synchronises directly to an external source"), and obtains the Proxmox UI certificate by ACME from `draupnir` (AD-5: "Proxmox natively"). Unit B is the same Procedure written by a builder reading the paradigm table literally — "a layer may depend only on layers strictly below it," L1 is below L2 — so it builds Nodes with local accounts only, an RTC-plus-hardware-clock time policy, and a self-managed certificate, treating identity/time/TLS as later enhancements. Both are compliant: AD-1 forbids upward dependency *into Yggdrasil* and says nothing about L1 depending on L2, while the paradigm forbids it and has no AD behind it. Incompatible because the two Node builds produce different `/etc/chrony.conf`, different `/etc/sssd/sssd.conf` (present vs absent), and different certificate lifecycles, and only Unit A can satisfy FR-20/FR-28/SM-3 while only Unit B can cold-start when `mimir` is down — which is every full-power-loss recovery, since `mimir` is a Guest on the Nodes that need it. *Fix:* new **AD-19 — the L1/L2 mutual dependency is declared and bounded**: state explicitly that L1 consumes identity, time, and certificates from L2 while L2 runs as Guests on L1, that this is a permitted mutual dependency and the only one in the design, and that every L1 consumption of an L2 service must degrade rather than block — SSSD with a bounded offline cache (AD-10), chrony with a documented local-clock fallback and a stated maximum acceptable cold-start skew, and certificate expiry that produces a warning, never a refusal to boot or to authenticate a Break-glass session. Add the cold-start ordering to the Procedure Index as a named Procedure ("cold start with the Directory down").

- **[critical]** OpenTofu state is unnamed, unowned, and secret-bearing (procedures/secrets) — Unit A is `l1-hypervisor/` built by the S2 epic, which commits `terraform.tfstate` to the Repository on the strength of AD-4 ("no configuration required to rebuild any component exists solely on a running system") and SOPS-encrypts it to satisfy AD-15. Unit B is `l2-foundation/opentofu/` built by the S4 epic, which puts state in an object-storage backend so `tofu apply` is safe to run twice — hosted on Nidavellir or on MinIO in Yggdrasil, since those are the only object stores available. Both obey AD-4 and AD-15 as written. Incompatible because Unit A's SOPS-encrypted state cannot be locked, so any concurrent or CI-driven apply corrupts it, and Unit A's state contains `cipassword` and generated secrets in cleartext-within-the-blob, meaning the age key is now the only thing between GitHub and every Guest credential; Unit B makes L1 provisioning depend on L3/L4 storage, so a Node cannot be rebuilt while the cluster is down — which is precisely the SM-1 Drill. Neither builder is wrong under the current spine, and the state file is not in AD-9's escrow list, so losing it loses the ability to converge L1 at all. *Fix:* new **AD-20 — declarative-provisioning state is a first-class, named, escrowed artifact**: name the backend, require it to live outside both Yggdrasil and Nidavellir (local encrypted file plus escrow copy, or the same SanDisk escrow as AD-9), forbid committing raw state to the Repository, require state encryption at rest with the key in the AD-9 escrow set, and forbid provider resources that write secret material into state where an alternative exists (no `cipassword`; SSH keys only).

- **[critical]** AD-1's controller clause covers L0 and L1 only, so a Workload may legitimately own L2 (layering/procedures) — Unit A is `brokkr` (Actions Runner Controller, placed in Yggdrasil by AD-18 with "test met: none") running the `l2-foundation/` Ansible pipeline on a schedule, which is how AD-4's "changes made directly against a running system are reverted by the next reconciliation" is actually enforced for non-Kubernetes layers — there is no other reconciler in the design. Unit B is a workstation-run or Node-run Ansible invocation for the same content. Both comply: AD-1's concrete clause says "no controller managing L0 or L1 infrastructure runs as a Workload," and L2 is neither. Incompatible because Unit A makes the Directory, DNS, Kerberos, time, and the platform CA reconcilable only while Yggdrasil is up — the exact inversion AD-1 exists to forbid, arriving through a clause that enumerates two layers instead of stating the principle — while Unit B leaves AD-4 with no enforcement mechanism below L3 at all, so "reverted by the next reconciliation" is false for two-thirds of the platform. *Fix:* tighten **AD-1** to "no controller or runner that manages any layer below Yggdrasil runs as a Workload," and add to **AD-4** the reconciliation-agent clause: name, for each layer, what runs the reconciler, from where, and on what trigger; where a layer has no automatic reconciler, AD-4's guarantee is downgraded in writing to "drift is detected by a scheduled convergence check (AD-3)" rather than "reverted."

- **[critical]** AD-9's escrow set is insufficient to rebuild the platform (secrets) — Unit A is the D7 secrets epic, escrowing exactly what AD-9 names: Break-glass credentials, the Kubernetes static administrative credential, and the platform CA root key. Unit B is the S1 epic, which introduces SOPS+age for Repository secrets before any secret store exists and keeps the age private key on the operator's workstation, because AD-15 only requires "a key held outside" the Repository. Both are literally compliant. Incompatible with FR-64 rather than with each other, and that is worse: after a workstation loss the Repository is intact, the escrow is intact, AD-9 is satisfied, and *every encrypted value in the Repository is unrecoverable* — no Guest passwords, no service credentials, no realm configuration. The same hole swallows OpenBao's unseal/recovery keys (andvari cannot unseal itself), the FreeIPA Directory Manager password, the DSM administrative credential the synology-csi driver needs, the Argo CD repository credential, and the DNS TSIG key if dynamic updates are used. *Fix:* tighten **AD-9** from a list of three items to a rule plus a maintained set: "the escrow set is enumerated in the Repository and contains every credential without which a rebuild from Repository plus backups cannot proceed; adding any new root-of-trust — an encryption key, an unseal key, a directory master password, a forge credential — adds a row in the same change." Make the escrow enumeration a Procedure with a verification step (a restore Drill that uses only the escrow).

- **[critical]** L3 cluster components take their credentials from an L4 service, inverting the mermaid's own dotted arrow (layering/secrets) — Unit A is the D1 storage epic wiring `synology-csi`, which needs a DSM API credential, and Unit B is the D3 platform epic wiring cert-manager with an RFC2136 DNS-01 solver, which needs a TSIG key. Both builders reach for the platform's stated secret-delivery mechanism — External Secrets from `andvari` — because AD-15 says workload secrets are "delivered at runtime" and the D7 epic exists to provide exactly that. Both compliant. Incompatible with the architecture rather than each other: `andvari` is L4, placed inside Yggdrasil under AD-18 with "test met: none," and it needs a PersistentVolume (L3 CSI) and possibly a database to start. A cold start now requires CSI → andvari → CSI. The spine's own diagram marks L3→L4 as "enhancement only, never required"; nothing enforces it, and AD-18's four tests are asked of the *service being placed*, never of the *consumer*, so they cannot detect this. *Fix:* new **AD-21 — L3 components bootstrap without L4**: every credential required by a cluster component (CSI drivers, cert-manager, MetalLB, the gateway) is delivered by the same mechanism that installs the cluster component itself — SOPS-in-Repository decrypted at apply time — and never by the runtime secret store. Add a fifth AD-18 test applied to consumers: "if a layer at or below the candidate's layer requires it to start, the candidate is misplaced."

- **[critical]** A secret that never enters the Repository satisfies AD-15 completely (secrets) — Unit A is the S5 epic delivering `forseti`, whose thin form is permitted by the PRD; the builder creates the Keycloak admin credential and the FreeIPA bind credential with `kubectl create secret generic` and records nothing, reasoning correctly that AD-15 governs "secret material committed to the Repository" and nothing was committed. Unit B is the D6 epic, which SOPS-encrypts its secrets into the Repository. Both obey AD-15; Unit A obeys it more completely, since it cannot possibly leak. Incompatible with AD-4 and FR-64: Unit A's credential exists solely on a running system, which AD-4 forbids for "configuration" — and the spine never says a secret is configuration. A cluster rebuild (FR-40) silently loses it, and no convergence test detects it because AD-3 tests Runbook-vs-Automation, not Repository-vs-reality. *Fix:* tighten **AD-15** to make the obligation two-sided: "every secret the platform requires exists in exactly one of two authoritative locations — encrypted in the Repository, or in the runtime secret store whose own contents are backed up and whose unseal material is escrowed under AD-9. A secret that exists only as a live object on a running system is a defect, identically to plaintext in the Repository." Add a stated rule for which of the two locations governs which class of secret, so the choice is not per-builder.

- **[critical]** The Directory's POSIX ID range is not pinned, so a rebuilt Directory orphans every NFS home directory (identity/storage) — Unit A is the S4 epic installing `mimir` with `ipa-server-install` defaults, which allocate a *randomly chosen* base for the POSIX UID/GID range at install time; homes are then created on Nidavellir owned by, say, `1247800001`. Unit B is the D11 rebuild Drill, or any FR-64 recovery, which reinstalls `mimir` from the Repository and restores directory data — and if the range is not explicitly declared, or if data is restored into a fresh install rather than from a full backup, the operator's account is issued a different UID. Both obey AD-2 (accounts only in the Directory), AD-4 (definitions in the Repository), and FR-26. Incompatible because NFSv3 `sec=sys` carries numeric IDs: every file in every Home Directory and every NFS-backed PersistentVolume is now owned by a UID that no longer resolves, FR-15 and SM-7 fail silently, and the failure surfaces as "my files are gone" long after the rebuild is declared successful. Nothing in the spine names the ID range as a configuration item. *Fix:* new **AD-22 — numeric identity is pinned, declared, and escrowed**: the Directory's POSIX ID range base and size are declared in the Repository and passed explicitly at install (`--idstart`/`--idmax`), local system accounts on every host are constrained to a range that provably cannot collide with it, the range is recorded alongside the address plan, and the FR-64 rebuild Procedure verifies the operator's UID matches the pre-rebuild value before any home directory is remounted.

### High

- **[high]** Database multiplicity and shared-database ownership are ungoverned (databases) — Unit A is the D6 observability epic, which gives Grafana its own three-instance CloudNativePG `Cluster` on local-path NVMe, credentials from the operator-generated Secret CNPG produces, schema owned by Grafana's own migrations. Unit B is the D5/D10 epic, which adds a database and role inside the shared `fafnir` cluster for Harbor and for `forseti`, credentials from `andvari` via External Secrets, schema owned by a migration Job in the Repository. Both obey AD-8 (both on local NVMe, neither on Nidavellir), FR-46 (isolated, documented, no plaintext), and AD-15. Incompatible on four axes at once: capacity (each additional 3-instance CNPG cluster consumes memory NFR-6 protects, and no AD governs NFR-6 at all), backup (FR-47's schedule and verified restore are written per-cluster in D9 against `fafnir`, so Unit A's data is outside it and nobody notices), NFR-22 (adding a Workload no longer follows one Procedure — there are two), and shared-instance ownership (with `fafnir` shared, no unit owns `max_connections`, `shared_buffers`, `pg_hba`, or the major-version upgrade, so two epics tune the same cluster in opposite directions). *Fix:* new **AD-23 — one PostgreSQL service, per-database tenancy, one provisioning Procedure**: `fafnir` is the single cluster; a Workload receives a database and role within it, never its own cluster, unless it names a stated exception; the cluster's own parameters, version, and backup are owned by the L4 stateful-services Procedure and are not editable from a Workload's declaration; schema ownership belongs to the Workload, database and role creation to the provisioning Procedure, and credential delivery to exactly one mechanism named in AD-15's two-sided rule.

- **[high]** Two owners of DNS records for published Workloads (shared entities) — Unit A is the D3 platform epic deploying `external-dns` with the RFC2136 provider, watching Gateway and HTTPRoute hostnames and writing A records into `mimir`'s zone, which satisfies FR-41's "publishing a new Workload requires no manual DNS step" exactly. Unit B is the S2/D-network epic committing a wildcard `*.asgard.home.arpa` record pointing at the MetalLB ingress address into the zone file the Ansible role manages, which satisfies the same requirement with no controller at all. Both obey AD-4 (declared in the Repository), AD-13 (internal only), and AD-14. Incompatible because Unit A makes zone content generated from live cluster state — so the records exist solely on a running system, breaking AD-4 — and requires dynamic updates plus a TSIG key on the Directory, an L4 controller writing into L2; Unit B makes every unresolvable name in the domain answer with the gateway address, which quietly destroys FR-34/AD-14's bypass-prevention reasoning ("its published name resolves only to the proxy" is meaningless when *every* name resolves to the proxy) and makes a typo indistinguishable from a service. Run together they fight over precedence. *Fix:* new **AD-24 — the Directory owns every DNS record; publication does not create records**: zone content is declarative in the Repository and applied by the L2 Procedure only; a Workload's published name is added as a record in the same change that adds its HTTPRoute; no controller inside Yggdrasil writes to the zone; if a wildcard is used it is stated as a deliberate decision with the bypass consequence recorded, not adopted as a convenience.

- **[high]** Two allocators of one address space (shared entities) — Unit A is the S2 network epic writing the address plan into `l0-physical/address-plan.md` per FR-12 and the addressing convention, reserving a block for future Guests. Unit B is the D3 platform epic writing `IPAddressPool` into `l3-platform/metallb/`, which must be on the same flat LAN subnet because MetalLB runs in L2 mode. Both obey AD-4 and the "address plan in the Repository, never discovered from running systems" convention. Incompatible because the two blocks are allocated independently, on the same /24, with no arbiter — and worse, both must sit outside the household router's DHCP pool, which is the one boundary the operator cannot manage and the spine never records as a fact. AD-4's "managed network devices are configuration items" does not reach the Google router. *Fix:* tighten the addressing convention into **AD-25 — one address plan file, one allocator**: a single file in the Repository is the sole allocator for every address in the Asgard subnet, including the MetalLB pool, the membership subnet, and the reserved-for-future ranges; the household DHCP pool boundary is recorded there as an observed external constraint with the date and method of observation; a component's declaration references the plan rather than restating an address, and any second file containing an address is a defect.

- **[high]** Two owners of authorization: Directory Groups vs IdP realm roles (shared entities) — Unit A is the D10 SSO-breadth epic, which defines `platform-admins` in the Directory, federates it into `forseti`, and maps it to client roles per Relying Party in the realm configuration, so authorization is expressed in Keycloak. Unit B is the D3 epic, which binds the raw group claim directly in a Kubernetes ClusterRoleBinding and never creates a Keycloak role at all. Both obey AD-2 — which forbids creating *Accounts* in the IdP and says the IdP stores "clients and realm configuration," and role mappings are plainly realm configuration — and both obey FR-31. Incompatible because Unit A introduces a second place authorization must be edited, directly contradicting SM-3's "with no second system edited," while Unit B makes the group claim's exact name and format a hard contract every Relying Party must agree on, which nothing specifies. Revoke a Group membership in the Directory and Unit B's access ends; revoke it and Unit A's access ends only if the role mapping is group-derived rather than user-assigned, and AD-2 does not forbid user-assigned roles. *Fix:* tighten **AD-2** with an authorization clause: "authorization is expressed as Directory Group membership and consumed by Relying Parties from a single named claim; the IdP maps Groups to claims and performs no authorization of its own — no user-assigned roles, no realm-local groups. The claim's name and value format are fixed in the Repository and identical for every Relying Party." Name the claim in the spine.

- **[high]** Two controllers writing the same Kubernetes Secret (secrets) — Unit A is the D6 epic, which commits SOPS-encrypted `Secret` manifests decrypted by an Argo CD plugin at render time. Unit B is the D7 epic, which commits an `ExternalSecret` and lets ESO materialise the same Secret name in the same namespace from `andvari`. Both obey AD-15 (encrypted at rest, key outside, delivered at runtime, rotation without editing the Workload declaration). Incompatible because Argo CD sees ESO's object as out-of-sync and prunes or overwrites it while ESO refreshes it back, producing a reconciliation loop that presents as intermittent authentication failure in whatever consumes the Secret; and because the two have different rotation semantics — rotating Unit B's value is invisible to Git, so AD-4's "determinable from the Repository" becomes false for that value. *Fix:* covered by the two-sided **AD-15** tightening above, plus an explicit rule: for any given secret, exactly one mechanism owns the resulting object; SOPS-in-Repository governs bootstrap and cluster-component credentials (AD-21), the runtime store governs Workload credentials, and a namespace/name may be produced by only one of them — enforced by the commit-time check that already exists for plaintext.

- **[high]** Gateway cardinality is unspecified and the shared address makes divergence collide (gateway) — Unit A is the D3 platform epic creating one shared `Gateway` in the gateway namespace with `allowedRoutes.namespaces: All`, so every Workload attaches an HTTPRoute to it. Unit B is a Workload epic creating its own `Gateway` in its own namespace, pinning `spec.addresses` to the same MetalLB address using the shared-IP annotation, on the reading that AD-14 mandates one *address*, not one Gateway. Both obey AD-14 verbatim. Incompatible because two Gateways cannot both bind :443 on one shared MetalLB address — MetalLB's shared-IP requires disjoint ports — so the second Service stays pending and the failure appears as "my route doesn't work" with no obvious cause; and because listener-level TLS, `SecurityPolicy` attachment, and the AD-10 propagation bound are all per-Gateway, so per-Workload Gateways multiply every one of them. *Fix:* tighten **AD-14** with cardinality and attachment: "exactly one Gateway exists, in a named namespace, owned by the L3 platform Procedure. Workloads own HTTPRoutes and attach to it by reference; a Workload that creates a Gateway, a Listener, or a LoadBalancer Service is a defect. Adding a listener is a change to the platform Procedure, not to a Workload."

- **[high]** Two TLS issuance strategies that cannot share a listener (gateway/PKI) — Unit A configures a single wildcard `*.asgard.home.arpa` certificate on the Gateway listener, issued by cert-manager over ACME DNS-01 against `draupnir`, which requires dynamic DNS updates and a TSIG key on `mimir`. Unit B configures per-hostname certificates issued over ACME HTTP-01 through the Gateway itself, one Certificate per published name. Both obey AD-5 ("all platform issuance and renewal happens over ACME... Kubernetes via cert-manager") and AD-14. Incompatible because Unit A drags in a DNS write path owned by nobody (see the DNS finding) and grants a key that can rewrite the Directory's zone to a controller inside the cluster, while Unit B requires every hostname to resolve *before* issuance, which inverts the ordering Unit A's wildcard assumes; and a listener cannot serve both a wildcard and per-host certificates for overlapping names without an explicit precedence decision no builder is directed to make. *Fix:* new **AD-26 — one ACME challenge type, one certificate topology, per consumer class**: state the challenge type for each of the four ACME consumers (cert-manager, Proxmox, hosts, the NAS), state whether the Gateway uses a wildcard or per-host certificates and why, and forbid granting DNS write credentials to any component inside Yggdrasil (which forces HTTP-01 or a self-hosted solver, and makes the choice once rather than per-Workload).

- **[high]** Guest OS family is unpinned for every role except two (host builds) — AD-17 pins the hypervisor to Debian-family and Directory Guests to RHEL-family and requires "a host-build Runbook per family," which the Procedure Index then carries as exactly two. Unit A builds Control Plane and Worker Guests on Debian, matching the hypervisor role and reusing `node_base`. Unit B builds them on Rocky, matching the IPA-enrollment role and the `draupnir` Guest. Both obey AD-17 — the rule constrains two roles and requires family-awareness, not family-selection. Incompatible because the two produce genuinely different platforms: SELinux enforcing versus absent changes k3s installation flags, container runtime policy, and the NFS-home boolean; firewalld versus nftables changes how the membership interface is protected; package names, service names, and the trust-anchor path all differ; and the "one Runbook per family" count in the Procedure Index becomes wrong the moment a role exists in both families. *Fix:* tighten **AD-17** to pin family per role, not per two roles: publish a table of every host role — Node, Control Plane Guest, Worker Guest, Directory Guest, CA Guest — with its OS family and the reason, and state that a role exists in exactly one family unless a named reason says otherwise. Add the SELinux posture as an explicit decision rather than a downstream consequence of family choice.

- **[high]** Two heartbeats to one dead-man's switch defeat the dead-man's switch (alerting) — Unit A is the D6 observability epic, which configures Alertmanager's heartbeat receiver to ping the external check on a schedule, satisfying AD-12's third path. Unit B is the D8 power epic, which adds a cron heartbeat from the NUT/NAS side because AD-12 says infrastructure alerting must not route through Yggdrasil and the operator wants the heartbeat to survive cluster loss. Both obey AD-12; both are outbound-only. Incompatible because a dead-man's switch fires on *absence*, so two independent senders to the same check mean the check stays green while either sender lives — the exact silence AD-12 exists to detect is now masked by whichever component did not fail. The memlog marks this path load-bearing during a whole-house outage, which makes a masked failure the highest-consequence one in the design. *Fix:* tighten **AD-12** with cardinality and origin: "exactly one dead-man's-switch heartbeat exists; its sender, its interval, and its grace period are named in the Repository; the sender is chosen so that its silence implies platform silence, and any second sender to the same check is a defect." Add a verification step: a Drill that stops the sender and confirms the external alert arrives.

- **[high]** "Native per system" backup leaves whole data classes unowned (backup) — Unit A is the D9 epic implementing the capability map's "Backup and recovery — Native per system": Synology snapshots plus Hyper Backup for NFS data, Proxmox vzdump for Guests, CNPG barman for PostgreSQL. Unit B is any epic that follows AD-8 and places data on local NVMe — Guest root disks, CloudNativePG data, and any local-path PersistentVolume. Both are fully compliant. Incompatible because the union of Unit A's three mechanisms does not cover Unit B's placements: a local-path PV inside a Worker Guest is captured only incidentally by vzdump of that Guest, crash-consistently, while the Guest is running k3s and etcd; and k3s's embedded-etcd snapshots default to local disk on the Control Plane Guest, so the snapshot dies with the Guest it protects. FR-61 requires coverage to be enumerated with deliberate exclusions listed; the spine turns that into a two-word convention with no owner. *Fix:* new **AD-27 — every persistent data location maps to exactly one named backup mechanism, in one enumeration**: the Repository holds a coverage table with one row per data location (NFS share, local-NVMe PV, Guest root disk, etcd, Directory data, registry blobs, secret store), naming its mechanism, its schedule, its destination, and its verified-restore Drill; a new data location without a row is a defect; etcd snapshots have an explicit off-Guest destination.

- **[high]** Capacity is an entire NFR class with no AD and no owner (capacity) — Unit A is the D3 epic sizing three Control Plane Guests and three Worker Guests generously because NFR-9 only requires that limits be *explicit*, not that they be small. Unit B is the D5/D6/D7 epics adding `fafnir`, `ratatoskr`, `huginn`, `muninn`, `gjallarhorn`, `sindri`, `brokkr`, and `andvari`, each declaring a reasonable request. Both obey every AD — there is no AD governing capacity, and the Capability→Architecture map has no capacity row. Incompatible with NFR-6's two-sided ceiling (90 GB committed, 15 GB schedulable) and NFR-7's single-Node-loss survivability, and the violation is only detectable *after* both epics land, at which point the remedy is redesign rather than adjustment. The PRD explicitly restated NFR-6 because the earlier metric was gameable; the spine dropped it entirely. *Fix:* new **AD-28 — capacity is a declared budget, allocated in the Repository before it is consumed**: a capacity ledger in the Repository allocates memory to every Guest and a Yggdrasil-wide reservation floor; a component's declaration draws from its allocation and adding one requires a ledger change in the same commit; the ledger states the NFR-6 ceiling and the NFR-7 three-Node residual, and CI checks the sum.

- **[high]** "The boundary is the guest's first boot" is ambiguous for exactly the things that matter (procedures) — Unit A is the S2 epic's OpenTofu module for Guests, which sets `ipconfig0`, `ciuser`, `cipassword`, and `sshkeys` on the Proxmox cloud-init drive: the Guest's static address and its Break-glass account are Proxmox resource attributes, so OpenTofu owns them, and AD-9 and FR-12 are satisfied at creation. Unit B is the S2/S4 epics' Ansible roles `network` and `breakglass`, which write the same address into the in-guest network configuration and create the same local account with the same escrowed password: an IP address and a `/etc/passwd` entry are in-guest configuration, so Ansible owns them. Both obey the convention — cloud-init *runs at* first boot, so it sits exactly on the boundary the convention draws, and the convention does not say which side. Incompatible because the address and the Break-glass credential now have two authoritative declarations in two directories, AD-3's convergence test cannot detect the drift (OpenTofu never inspects in-guest state; Ansible never inspects `ipconfig0`), and a Guest recreated from its declaration (FR-8) silently reverts whichever half Ansible owned. *Fix:* tighten the declarative-provisioning convention into **AD-29 — the boundary is the artifact, not the moment**: OpenTofu owns Proxmox API objects and hands the Guest exactly one thing — a reachable SSH endpoint with one bootstrap key — and nothing else; every account, address, package, mount, and file inside the Guest is Ansible's, including the Break-glass account and the interface addressing; cloud-init is used only to install the bootstrap key and is forbidden from carrying passwords, users, or addressing.

- **[high]** Proxmox host operating-system configuration is owned by neither clause (procedures) — Unit A is the S2 epic treating the Node as a Proxmox resource: OpenTofu's Proxmox provider configures node network interfaces (the membership bridge, the 2.5 GbE bridge), the ACME account and certificate, cluster options, and users/roles — all real provider resources, all "Proxmox resources" by the convention's words. Unit B is the S2 epic treating the Node as a host: an Ansible role writes `/etc/network/interfaces`, installs the trust anchor, configures chrony and SSSD, and disables wireless. Both obey the convention — a Node is not a Guest, so "Ansible owns in-guest configuration" does not reach it, and it is not a Proxmox *resource* either, since it is the thing hosting them. Incompatible because AD-7's membership-interface configuration is the single most safety-critical file in the design and the two units write it from different sources with different idempotence semantics; because OpenTofu's node-network resources and a hand-written interfaces file will fight on every apply; and because AD-3's convergence test is defined per-Procedure, so two Procedures each report zero changes while the running system oscillates. *Fix:* extend **AD-29** to name the L1 host explicitly: OpenTofu owns the Proxmox *cluster and its API objects* (Guests, storage definitions, pools, users, roles, ACME registration); Ansible owns every Node's operating system, including network interfaces, time, trust anchors, SSSD, and interface naming; the Node's `/etc/network/interfaces` has exactly one writer and it is Ansible.

### Medium

- **[medium]** Break-glass account naming has two readings of "unique per host" (host builds) — Unit A's Debian host-build role creates `bg-odin`, `bg-thor`, encoding the host in the name; Unit B's RHEL role creates a single name `breakglass` everywhere with a distinct password per host. Both obey AD-9 ("a named local administrative account with privilege escalation, unique per host") and NFR-13 ("unique per host, not shared") — the ambiguity is whether the *name* or the *credential* is what varies. Incompatible because the escrow record format, the Ansible connection variable for a Break-glass run, and the FR-64 recovery Runbook's literal `ssh` line all differ, and a recovery Runbook that names the wrong account is a Runbook that fails during the emergency it exists for. *Fix:* tighten **AD-9** to state the account name convention literally, and require that the FR-64 Runbook contain the exact login string.

- **[medium]** Two host-build Procedures set two different offline-cache bounds (identity) — Unit A's Debian role sets the SSSD credential expiry to one day; Unit B's RHEL role sets seven. Both obey AD-10 ("an explicit maximum age set rather than left at product default") and FR-22. Incompatible because SM-3 measures revocation against "the offline-cache expiry," singular, and AD-10's per-Relying-Party table has one row for hosts; with two values the recorded bound is wrong for half the fleet, and the wrong half is unknowable from the table. *Fix:* tighten **AD-10** to state the offline-cache bound as a single number fixed in the Repository, referenced by both host-build roles rather than restated in each.

- **[medium]** Trust-anchor distribution has two automated paths and an unstated enrollment scope (PKI) — Unit A ships `draupnir`'s root into the OS trust store per family (`/usr/local/share/ca-certificates` + `update-ca-certificates`; `/etc/pki/ca-trust/source/anchors` + `update-ca-trust`). Unit B installs it into the Directory with `ipa-cacert-manage` so enrolled hosts receive it through IPA. Both obey AD-5 (the anchor is not an issued certificate, so "ACME only" does not apply) and FR-28 ("installed by Automation"). Incompatible because Unit B's coverage is exactly the set of IPA-enrolled hosts and the spine never states which hosts are enrolled — are Control Plane and Worker Guests enrolled? are the Nodes? — so the two units disagree about which machines end up trusting the platform CA, and rotation produces two anchors with different serials in two stores. *Fix:* tighten **AD-5** with a distribution clause naming one mechanism and one rotation path, and add an enrollment-scope row to the AD-18 placement table or the conventions table stating which host roles are Directory-enrolled.

- **[medium]** The Directory replica's own time source, and the cold-start case, are unstated (time) — Unit A configures the replica to synchronise from `mimir`, chaining; Unit B configures both Directory instances upstream, reading "the Directory" as the two-instance service. Both obey AD-6 ("the Directory alone synchronises upstream"). Incompatible because Unit A's chain means a `mimir` outage leaves the replica's clock free-running while it is still serving Kerberos, and Unit B's parallel configuration means an uplink flap can split the two Directory instances' clocks — both failure modes in a system where five minutes of skew is fatal. Neither unit addresses the cold start, where every Node must reach correct time to boot the Guest that provides it. *Fix:* tighten **AD-6** with three named cases: the replica's source, the behaviour when the uplink is down, and the cold-start ordering with a stated maximum acceptable RTC skew and the recovery step when it is exceeded.

- **[medium]** Four ACME consumers, four provisioners, four certificate lifetimes (PKI) — Unit A registers a cert-manager ACME issuer against `draupnir` with short-lived certificates and cert-manager's own renewal cadence; Unit B configures `acme.sh` on hosts and on the NAS against a separately created provisioner with a much longer lifetime and a daily cron. Both obey AD-5 exactly. Incompatible with FR-29's second clause — "renewal failure raises an alert before the certificate expires" — because a lifetime shorter than the alerting evaluation interval leaves no window in which to alert, and because provisioner-level policy (allowed SANs, maximum duration) diverges per consumer, so a certificate that issues for one consumer is refused for another. *Fix:* tighten **AD-5** with a provisioner and lifetime clause: the provisioners, their names, their allowed name policies, their maximum durations, and the renewal-lead-time-to-alert relationship are stated in the Repository as one table.

- **[medium]** AD-3's convergence test is undefined for OpenTofu (procedures) — Unit A's L1 Runbook ends with explicit `tofu import` steps so that a hand-built Node or Guest is adopted into state and `plan` reports no changes, satisfying AD-3 literally. Unit B's Runbook ends with "run the Automation," which for a hand-built Guest means `tofu apply` *creating a second one*. Both obey AD-3's words; only Unit A obeys its intent. Incompatible because Unit B's Procedure is destructive on the exact path SM-2 measures, and because the two Runbooks now have different shapes for the same class of work. *Fix:* tighten **AD-3** to define convergence per automation technology: for Ansible, a check run reporting no changes; for OpenTofu, a plan reporting no changes *after* the import steps the Runbook must contain; state that a Runbook whose Automation would recreate what the Runbook built is defective.

- **[medium]** AD-8's iSCSI clause selects by preference, which is what AD-18 was written to forbid (storage) — Unit A chooses the NFS default class for a Workload's volume; Unit B chooses the iSCSI class for an identical Workload because it "wanted block semantics." Both obey AD-8, whose criterion is literally the word "wanted." Incompatible because a ReadWriteOnce iSCSI volume pins the pod and changes rescheduling behaviour that FR-17 requires, because the D9 backup path differs (file-consistent folder snapshot versus crash-consistent LUN snapshot), and because synology-csi brings a DSM credential dependency the NFS driver does not. *Fix:* tighten **AD-8** to replace "where block semantics are wanted" with an AD-18-style test: iSCSI is used if and only if the workload requires a filesystem it formats itself, or single-writer semantics it depends on for correctness; the reason is recorded per volume, exactly as placement is recorded per service.

- **[medium]** Published hostname scheme is undecided between three defensible readings (gateway/naming) — Unit A publishes Grafana at `huginn.asgard.home.arpa`, reading AD-16 to mean the Norse registry name is the public name. Unit B publishes Harbor at `registry.asgard.home.arpa`, reading AD-16 to govern component names while public names describe function. A third reading puts everything under paths on one host. All obey AD-16 and AD-14. Incompatible because OIDC redirect URIs, forward-auth cookie scope (parent-domain versus per-host), certificate topology, and the DNS record set all follow from this choice, and a Workload built under one scheme cannot be re-hosted under another without re-registering it at the IdP. *Fix:* tighten **AD-16** with a publication clause: state whether a published endpoint's DNS label is the registry name or a functional alias, state that the two are not mixed, and state the cookie-scope consequence.

- **[medium]** Two forward-auth implementations, two session models, neither in the AD-10 table (gateway/SSO) — Unit A fronts a service with Envoy Gateway's native OIDC `SecurityPolicy`, which holds its own session cookie with its own lifetime; Unit B fronts another with a separate `oauth2-proxy` behind an ext-auth policy, with a different cookie, a different refresh behaviour, and a different logout path. Both obey AD-14 and FR-34. Incompatible because AD-10 requires each Relying Party's propagation bound to be recorded and declares an unrecorded bound a defect — and neither builder recognises that their proxy's cookie lifetime, not the IdP's 15-minute token, is the real bound for the service behind it, so both bounds go unrecorded while both builders believe they complied. *Fix:* tighten **AD-14** to name one fronting mechanism, and tighten **AD-10** to state that the bound recorded for a fronted service is the *proxy session* lifetime, not the token lifetime.

- **[medium]** The S5 thin form places a database on the class AD-8 forbids it on (storage/sequencing) — Unit A is the S5 epic taking the PRD's explicitly permitted thin form: `forseti` on an embedded database, whose volume the builder places on the default NFS class because AD-8 permits NFS for "general Workload volumes" and an embedded file database is not obviously `fafnir`. Unit B is the D5 epic migrating it to `fafnir` on local NVMe. Both are sanctioned. Incompatible because AD-8's first sentence — "nothing performing database-class random I/O is placed on it by any protocol" — forbids Unit A outright, and the spine never reconciles this with the thin form the PRD grants; a builder who obeys AD-8 must place the embedded database on local-path NVMe, which pins the pod to a Node and makes the S5→D5 step a data migration nobody planned. *Fix:* add a sequencing clause to **AD-8** naming the permitted skeleton placement for the embedded IdP database and the migration step, so the thin form does not have to be reinvented against an AD that appears to forbid it.

- **[medium]** Managed-switch configuration cannot satisfy AD-3's dual form (procedures) — Unit A treats the easy-managed membership switch as a configuration item per AD-4 ("managed network devices are configuration items under this rule, not exceptions") and commits a binary configuration export, calling a restore script the Automation. Unit B writes a Runbook only and marks the entry as documentation-only. Both are defensible; AD-3 admits no exemption and AD-4 admits no exception, so Unit B is non-compliant and Unit A's "Automation" cannot be idempotent or convergence-tested, meaning neither can actually pass. Incompatible because the Procedure Index — the authoritative enumeration everything else is measured against — now contains an entry that no builder can complete, which teaches the operator that Index entries are aspirational. *Fix:* tighten **AD-3** with a stated exception class: devices with no idempotent configuration interface are recorded in the Index as Runbook-plus-captured-configuration, the deviation is named, and the verification is a diff of the captured configuration against the device, not a convergence run. An AD that cannot be satisfied for a known device class must say so.

- **[medium]** The measured shutdown margin lives in prose and in configuration, with no link (power) — Unit A is the D8 epic recording the Drill-measured margin as a number in a Runbook paragraph per AD-11. Unit B is the same epic's Ansible role and DSM settings, which encode the actual delays. Both obey AD-11. Incompatible because nothing ties the recorded number to the configured delays, so a later change to either drifts silently, and AD-3's convergence test compares Automation to system — never prose to configuration. The one number the design says must never be estimated is the one number nothing checks. *Fix:* tighten **AD-11** to require the margin be a *value in the Repository that the Automation reads*, with the Runbook citing that value rather than restating it, and the Drill's verification comparing the measured result to the value in place.

- **[medium]** Infrastructure alerts have two paths for the same condition (alerting) — Unit A is the D6 epic implementing FR-19 by scraping NAS capacity and drive health into the observability stack and alerting from there; Unit B is the D8 epic implementing AD-12 by configuring DSM's own notification for the same conditions, since infrastructure alerts "must not route through Yggdrasil." Both obey AD-12 and FR-19/FR-51. Incompatible in two directions: duplicated notification for every event, which trains the operator to ignore the channel, and — during a Yggdrasil outage — an assumption on each side that the other covers it, so a genuine drive failure may be alerted twice or reasoned about zero times. *Fix:* tighten **AD-12** to partition conditions rather than paths: state which conditions originate from the appliance and which from Yggdrasil, and state that a condition alerted from both is a defect.

### Low

- **[low]** The naming reserve pool has no allocation arbiter (naming) — two epics running concurrently each take the next name from the reserve pool and each add it to the registry in the same change, exactly as AD-16 requires. Both compliant; the merge conflicts or, worse, does not, and two components share a name. *Fix:* state in **AD-16** that the registry file is the allocator and an allocation is a change to it, so a concurrent take is a textual conflict rather than a silent collision.

- **[low]** Repository layout splits a component's two halves and the convention endorses both (procedures) — the layout says "one directory per layer (L0–L5); a Procedure's Runbook and Automation live adjacent," and the tree also shows top-level `runbooks/` and `ansible/`. Unit A puts a Procedure's two forms adjacent under its layer directory; Unit B puts the Runbook in `runbooks/` and the role in `ansible/`, per the tree. Both compliant, and the resulting tree is half one and half the other, so "adjacent, cross-referencing by name" holds for some Procedures and not others. *Fix:* pick one and delete the other from the shape diagram; if cross-cutting directories are kept, state that adjacency is satisfied by the named cross-reference rather than by location.

- **[low]** "Procedure" has no granularity rule, so the Index denominator is builder-defined (procedures) — Unit A writes one Procedure for "build a Node"; Unit B writes five for the same work (install, network, enroll, trust, verify). Both obey AD-3. Incompatible because SM-1 and SM-2 are ratios over the Index, so the denominator moves with authorship, and NFR-22's "follows an existing Procedure" is easier or harder to satisfy depending on how the neighbouring epic split its work. *Fix:* state a granularity rule in **AD-3** — one Procedure per operational activity with a single stated verification and a single outcome — so the Index counts comparable things.
