- (decision) Directory product: FreeIPA. Chosen because it delivers FR-21 (HBAC + central sudo), FR-25 (multi-master replication), FR-27-29 (CA), and FR-11-13 (DNS) as ONE system. LLDAP eliminated on requirements - SQLite-backed, no replication, so FR-25 is unmeetable. Samba AD DC was the real alternative; rejected because it brings no integrated CA.
- (constraint) FreeIPA server is only genuinely supported on RHEL-family, so Directory Guests run Rocky/Alma while Proxmox runs Debian. MIXED-OS is now a binding architectural fact: Ansible must handle two OS families from day one, and the Procedure Index carries two host-build runbooks.
- (constraint) Physical: DeskPi/GeeekPi RackMate T2 (12U, 10-inch, 10.23in depth) retained. Houses 4 Nodes + both switches + router (~8-10U of 12U). NAS shelved beside the rack (8.8in body leaves ~1.4in for cabling - too tight) and the SMT1500C on the floor (17.5in deep, 54lb - never fits a 10in rack, and heavy batteries belong low regardless). 19-inch rack deferred to a later purchase. Nodes need airflow gaps, not flush stacking.
- (constraint) Nidavellir is HDD-only: 4x WD Red Pro 14TB spinning disks, no SSD tier populated. This constrains any design that would place random-I/O workloads on NAS-backed storage.
- (decision) UPLINK SETTLED: TP-Link TL-WA3001 in Client (wireless bridge) mode connects the data switch to the Google WiFi router. REVERSES the earlier 'AP not deployed' decision - the rack has no wired path to the router (opposite side of house, Google WiFi with no spare ports, no coax anywhere). Zero cost, four external antennas suit a through-walls link. MoCA was preferred but ruled out - no coax in the house. Powerline and the GL.iNet BE3600 remain fallbacks.
- (constraint) The wireless bridge carries OUTBOUND traffic only: package updates, image pulls, NTP, alerts. Corosync, NFS, pod, storage and backup traffic never cross it - all stays on the two switches at the rack. A 100-200 Mbps bridge is therefore adequate; the bottleneck lands where it does not matter.
- (decision) TIME: FreeIPA is the authoritative internal time source; all Nodes and Guests sync to it, and FreeIPA alone syncs upstream when the bridge is available. Rationale: Kerberos breaks outright at ~5 min clock skew, and external NTP dies with a flaky wireless uplink. Internal time must stay coherent independent of the bridge. Becomes an AD.
- (constraint) POWER-ALERT PATH BROKEN BY TOPOLOGY: the Google router sits in a closet across the house on a circuit the operator does not control, so FR-58's 'router on UPS' is unachievable. In a whole-house outage nothing outbound can leave. Consequence: the healthchecks.io dead-man's switch is now LOAD-BEARING, not a nice extra - it alerts from external infrastructure to the phone over cellular when the heartbeat stops. Optional remedy: a small UPS in the router closet.
- (decision) ADDRESSING: lab devices take the Google WiFi LAN (typically 192.168.86.0/24). FR-12 determinism is met with static IPs outside the DHCP pool rather than DHCP reservations - Google's reservation UI is limited. The corosync segment is unaffected: private range, no gateway, never touches the Google router.
- (decision) AD-1 (the spine's central invariant): nothing Yggdrasil requires in order to START or to AUTHENTICATE may run inside Yggdrasil. Generalizes every circular dependency killed this session - the IdP-authenticated VPN, the Omada controller managing its own cluster's membership network, and FreeIPA-in-k8s. Keycloak passes despite kubectl OIDC because FR-39 mandates a static break-glass credential.
- (decision) Operator direction: ALL infrastructure services run as k8s workloads. Sole exception is FreeIPA (mimir + replica), which stays as Rocky/Alma VMs under AD-1 - k3s nodes resolve names through it and hosts authenticate against it, so k8s-hosted FreeIPA means k8s down => cannot authenticate to fix k8s. Kerberos also needs stable hostnames/PTR that pod networking complicates, and containerized FreeIPA is not a supported path.
- (decision) PostgreSQL REVERSED from 'VM on local NVMe' to CloudNativePG in Kubernetes on local-path NVMe PVs. Strictly better than the VM proposal: same NVMe speed, stays k8s-native per operator direction, AND survives Node loss via CNPG-managed streaming replication with automatic failover - which the single VM did not. iSCSI remains rejected: Nidavellir is HDD-only, so it would put database random I/O on spinning disks.
- (decision) CA topology: split. FreeIPA Dogtag issues only IPA's own internal certificates; step-ca becomes 'draupnir', the platform CA, speaking ACME. Proxmox has native ACME, cert-manager speaks ACME, hosts and DSM use acme.sh - so FR-29 auto-renewal across four heterogeneous consumers is nearly free, and the Dogtag renewal-master trap is contained to IPA.
- (decision) Alert channel: Pushover. Three independent tiers - Alertmanager (platform), DSM + NUT notify scripts (infrastructure, must survive platform loss), healthchecks.io dead-man's switch (total silence). All outbound-only, so NFR-14 holds.
- (decision) Synology RAID: SHR-2 (~28TB usable, two-drive tolerance). Chosen over SHR-1's ~42TB because with no independent backup the array's redundancy is the ONLY protection against total loss, and 14TB rebuild windows run 26-40 hours with material URE probability across the surviving set.
- (decision) Ingress/LB: bundled Traefik and ServiceLB DISABLED at k3s install. MetalLB in L2 mode provides real LoadBalancer IPs from a pool (gives FR-41 a stable ingress IP for DNS rather than node-IP fiddling); ingress-nginx is the ingress controller (industry standard, best-documented cert-manager/ACME path, strongest skill transfer for purpose B).
- (decision) TWO storage classes from Nidavellir: csi-driver-nfs as the DEFAULT class (ReadWriteMany, file-level, general workloads) and synology-csi iSCSI as a second class (ReadWriteOnce, block-level) for workloads wanting block semantics and their own filesystem. Explicit caveat: both land on the same 4 spinning disks, so iSCSI buys semantics not speed - it would not have rescued PostgreSQL.
- (constraint) CLARIFIED: Nidavellir still carries home directories (FR-15), persistent volumes (FR-17) and backups (FR-61/62). Only two things moved off it - Proxmox VM root disks and PostgreSQL data, both to local NVMe. Consequence for FR-57: a Node can stop its guests without touching the NAS, so the shutdown failure mode softens from 'VM disk vanishes mid-write' to 'data volume vanishes after its pod was drained'. Ordering unchanged; required margin smaller.
- (question) FUTURE: DS925+ has M.2 NVMe slots, unpopulated. An NVMe cache or NVMe storage pool (DSM 7.2+) would give Nidavellir a fast tier and make NAS-backed databases viable, changing the PostgreSQL placement calculus. Not v1.
- (decision) NUT topology CONFIRMED as PRD-specified: DSM is NUT server over USB, Nodes are clients, ordering by tuned delay. A Node-as-primary alternative is worse - if the primary shuts down first the secondaries lose their signal source. Starting values for the FR-60 Drill to validate: Nodes begin shutdown at ~3 min on battery, DSM enters safe mode at ~10 min - a 7 min margin against a ~5 min sequence inside 12-15 min runtime.
- (decision) Interim critical-subset backup (partial mitigation of the deferred FR-62 gap, zero cost): the Repository is already off-platform on GitHub; FreeIPA directory data, PostgreSQL dumps, the step-ca root key and Break-glass credentials go encrypted to the owned SanDisk 1TB portable SSD, which was already designated bootstrap seed and credential escrow. Does not close FR-62 - a dead NAS still costs bulk volumes - but it means identity, CA and databases survive.
- (version) VERIFIED 2026-08-28 via web: Proxmox VE 9.2; k3s 1.36.4+k3s1; FreeIPA 4.12.5 (verified on Rocky 10.1); Keycloak 26.7.2; CloudNativePG 1.29.1; step-ca 0.30.2; MetalLB 0.16.x; cert-manager 1.20; OpenTofu 1.12.2; Ansible 2.20.5.
- (decision) INGRESS REVERSED: ingress-nginx reached END-OF-LIFE 2026-03-24 - repository read-only, no CVE patches, Kubernetes Steering + Security Response Committees recommend immediate migration. Successor project InGate also retired. The transferability argument that justified ingress-nginx has inverted: it is now a dead skill and an unpatched attack surface.
- (decision) Gateway: ENVOY GATEWAY on Gateway API. Chosen over Traefik+GatewayAPI (lower effort, k3s-bundled) and NGINX Gateway Fabric. Rationale: Envoy is the data plane behind Istio/Cilium/most meshes so knowledge transfers furthest; CNCF vendor-neutral; matches the operator's original intent when picking ingress-nginx (industry-standard path, setup work accepted). MetalLB L2 retained - unaffected by the EOL, v0.16.x current.
- (decision) Gateway API is the ONLY north-south routing API. Ingress resources are not used - not even for migration convenience - so there is one routing model rather than two.
- (decision) GitOps controller: Argo CD. Chosen over Flux for the UI, and because it becomes another Keycloak Relying Party which serves the FR-32 SSO-breadth goal.
- (decision) CI: self-hosted GitHub Actions runners in Yggdrasil via Actions Runner Controller. The Repository already lives on GitHub, so this adds no new forge and no new identity domain.
- (decision) Registry: Harbor (OIDC-integrated, vulnerability scanning, RBAC - serves purposes A and B). Flagged as the FIRST optional cut if the NFR-6 capacity ceiling binds; a plain OCI registry satisfies FR-43 at roughly a tenth the footprint.
- (decision) Secrets, two stages matching the PRD's own S1 phrasing: SOPS + age for Repository-stored secrets from epic S1 onward (satisfies FR-53 before any secret store exists), then a runtime store as 'andvari' with External Secrets Operator for FR-54 delivery. Vault relicensed to BSL, so OpenBao (the OSS fork) is the default candidate - confirm at build time.
- (decision) Backup uses each system's native mechanism rather than a new abstraction layer: Synology Btrfs snapshots + Hyper Backup for NFS data (home directories, PVs); Proxmox vzdump for VM guests; CloudNativePG's built-in barman backup for PostgreSQL - all landing on Nidavellir. Velero deliberately NOT introduced. Critical subset additionally to the SanDisk per the interim decision.
- (decision) step-ca placement REFINED against the operator's all-in-k8s directive: it runs at the foundation layer alongside FreeIPA, NOT inside Yggdrasil. Hosts and Proxmox obtain TLS from it, so a CA living inside Yggdrasil makes the layer below depend on the layer above - the inversion AD-1 exists to forbid. Not a hard start/auth dependency (Proxmox degrades to a cert warning rather than failing), but renewal for every host would stall whenever the cluster is down.

- (decision) Operator AMENDED the all-in-k8s directive to 'in k8s where it makes sense; as a Proxmox VM where being inside would cause problems'. - (constraint) AD-28 amended after operator raised that the Nodes were wiped and reinstalled with Ubuntu, so defaults would be gone. CORRECTED: out-of-band management lives in firmware on the management controller with its own config store and network stack - OS reinstall, disk wipe and repartitioning do not touch it. Same failure shape as the Intel AMT exposures, where machines stayed vulnerable across reinstalls because a clean OS was read as a clean machine. AD-28 now requires POSITIVE verification (port probe from another host + firmware setup screen) rather than inference, and adds a firmware administrator password so the setting cannot be silently reverted by anyone with physical access.
- (decision) AD-3 tightened with an explicit RUNBOOK STANDARD after the operator chose delegated execution: Claude drives the Automation against the hardware, but the operator retains diagnosis. A Runbook must therefore be a COMPLETE MANUAL PROCEDURE - actual commands not 'run the playbook', expected output per checkpoint, bidirectional mapping between Runbook steps and Automation tasks so a failed task points at the section explaining it, and a failure-mode note on any step with a known way to break. Rationale: a delegating Runbook is worthless at the exact moment it is needed.
