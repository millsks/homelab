# Epic 1 Context: Repository, Procedure standard, and secret handling

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Epic 1 establishes how every subsequent story in the platform gets written. It creates the layered repository tree that mirrors the platform's dependency layers, an ownership table that names exactly one declaring owner for every configurable resource class, the Procedure Index that turns "every operational activity is documented" from an aspiration into a countable claim, the harness that proves runbooks and automation agree, and encrypted secret handling that works before any runtime secret store exists. Nothing here provisions hardware — it is the contract every later epic is graded against. Without the Procedure Index in particular, the platform's core documentation requirements quantify over an unbounded set and its two headline success measures (zero undocumented rebuild steps; convergence holds for every Procedure) have no denominator.

## Stories

- Story 1.1: Repository skeleton with layered ownership
- Story 1.2: Procedure Index and the dual-form contract
- Story 1.3: Convergence test harness
- Story 1.4: Encrypted secrets before a secret store exists

## Requirements & Constraints

- **Every operational activity is a Procedure with two halves.** A Procedure is a Runbook *and* its Automation; neither alone qualifies. Both halves must exist, be cross-referenced by name, and be listed in the Procedure Index with the owning layer. An Index entry missing either half is reported as an incomplete Procedure.
- **Convergence is the definition of done.** Automation run against a system built by hand from its Runbook must report zero changes. Any difference is a documentation defect closed at discovery — never accommodated by weakening the Automation. Automation is idempotent without exception: a second consecutive run also reports zero changes.
- **Procedures declare their own verification.** Every Runbook ends with a verification whose expected output is stated, and the verification is identical whichever path performed the work.
- **All configuration originates in the repository.** No configuration required to rebuild any component exists solely on a running system. Changes made directly against a running system are promoted into the repository or reverted.
- **No plaintext secret reaches the repository or its history.** Committed secret material is encrypted and unusable without a key held outside the repository; a commit-time check rejects plaintext and names the offending path. The decryption key is escrowed outside the repository and outside any single un-escrowed machine — a key held only on the operator's workstation fails this.
- **Documentation quality is a hard requirement, not a nicety.** A Procedure must be executable six months later by an operator with no recall of building it; ambiguity is a defect. Runbooks state reasoning, not only commands. Where a Runbook and its Automation disagree, the Automation is authoritative for *what* and the Runbook for *why*, and the disagreement is closed rather than tolerated. A change to a system and to its Procedure land together.
- **Automation coverage must not cost comprehension.** Automating a Procedure so thoroughly that its Runbook no longer explains the reasoning is a failure, not a win.

## Technical Decisions

- **Six stratified dependency layers, L0–L5**, with dependencies pointing only downward: L0 physical, L1 hypervisor, L2 foundation (directory, DNS, Kerberos, time, platform CA), L3 platform (Kubernetes, storage classes, gateway), L4 platform services, L5 workloads. The upward-dependency prohibition is the design's single enforceable claim. The repository tree mirrors these layers directly, one directory per layer, plus `runbooks/` for the human form and `ansible/` for in-guest configuration. A Procedure's Runbook and Automation live adjacent and cross-reference by name. `PROCEDURE-INDEX.md` sits at the repository root as the authoritative enumeration.
- **The Runbook standard is load-bearing.** A Runbook is a complete manual procedure, executable start to finish with no Automation available. Delegating to the Automation ("run the playbook") does not satisfy it, because it is worthless at the one moment it is needed — when that Automation has just failed. Each Runbook states the actual commands the Automation issues in order; states expected output at each checkpoint so a divergence is locatable rather than merely detectable; maps bidirectionally to its Automation, each step naming the task that performs it and each task naming its explaining section; and carries a failure-mode note on any step with a known way to break — what the failure looks like and what to check first. The execution model is that the operator delegates execution but retains diagnosis, which is exactly why this standard is not ceremonial.
- **Declarative ownership is total, exclusive, and split by attribute — never by moment.** Every configurable resource has exactly one declaring owner named in an ownership table. Coverage is total: the hypervisor host OS, the storage appliance, and every managed network device have owners, not just guests. "The guest's first boot" is not a boundary, because first-boot provisioning sits precisely on it. The provisioning tool (OpenTofu) declares virtual hardware and guest existence and hands over exactly one thing — a reachable SSH endpoint with a bootstrap key. The configuration tool (Ansible) declares everything inside the OS, *including* addresses and accounts that cloud-init could also set. Where a mechanism can express an attribute belonging to the other owner, leaving it unset is mandatory rather than stylistic. Provisioning state is itself an owned, versioned artefact with a stated location, locking behaviour, and escrow entry. No resource class may appear with two owners or none.
- **Drift detection differs by layer.** L3–L5 reconcile continuously with self-heal and prune. L0–L2 are push-based with no reconciliation loop, so they require scheduled check-mode runs where a non-empty diff exits non-zero and is recorded — it must not pass silently. Such checks register in the Procedure Index as alert sources; wiring them to actual notification happens in a later epic and is not a dependency of this one.
- **Three layers of work are genuinely manual** and their Runbooks have no Automation half at all: L0 physical (racking, cabling, outlet allocation, firmware), the hypervisor installation on each Node, and the storage appliance's initial setup. These are marked as such in the Procedure Index rather than left looking like automation gaps. Their verifications are still automated even where their execution cannot be.
- **Versions are pinned exactly; `latest` is prohibited.** Where a distribution package lags upstream, the distribution version is authoritative — it is what installs. Upgrades proceed bottom-up through the layers, and each layer's Procedure states its own rollback. Compatibility windows are checked pairwise at pin time; a component outside another pinned component's supported range is a defect, not a warning. Component EOL is reviewed before any epic depends on one.
- **Names come from the Norse registry in the planning artifacts, which is authoritative.** Realms name tiers; beings name instances. Hosts and services are lowercase and unqualified in inventory, FQDN under `asgard.home.arpa` in configuration. A new component takes a name from the reserve pool and is added to the registry in the same change.
- **Escrow is an exhaustive enumerated list in the repository**, not a set of examples, and the list is itself an artefact under review. The key that decrypts repository-stored secrets is one of its entries; every item names where it lives and how it is rotated.

## Cross-Story Dependencies

- Story 1.1 is the true first story of the whole platform — the repository skeleton and ownership table are what 1.2, 1.3, and 1.4 all land into. Nothing in any epic can be committed before it exists.
- Story 1.2 depends on 1.1's skeleton; 1.3's convergence harness operates on Procedures registered by 1.2's Index.
- Story 1.3's scheduled check-mode drift detection for the push-based layers registers as an alert source in the Index; the notification wiring lands in the observability epic (Story 13.5). This story must not be blocked on alerting existing.
- Every later epic inherits Epic 1's contract: each story delivers a Procedure that appears in the Index, and is not done until its Automation reports zero changes against a hand-built system. Failures to satisfy this in a later epic are defects against Epic 1's standard, not against the later story's feature.
- Story 1.4's escrow requirement anticipates the runtime secret store built much later; the two must not be confused — this epic's secret handling is what makes the repository publishable before any secret store exists.
